# GAP-11-G — A rebuild regenerates 1,330 of the anchors Plan 11-18 pruned

**Status:** open — blocks Plan 11-25 Task 3 (the live rebuild), and therefore SC7
**Found:** 2026-07-27 by the Plan 11-25 executor, on the rehearsal clone. The live corpus was never
written; `~/.memory/aaron.db` is `stat`-identical across the whole plan.
**Severity:** blocking. Applying the authorized rebuild today would undo a completed gap closure.

## What it is

Plan 11-18 permanently deleted 26,643 unhygienic anchors. A full `rebuild-derivations` pass on a clone
regenerates **1,330 of that exact deleted set**, and 1,330/1,330 contain raw `[Tool call: …]` text. The
product's own classifier agrees: `tool_activity: 1330` on the rebuilt clone vs `0` on live.

Measured at id level, not by count: the deleted set was reconstructed by differencing
`~/.memory/aaron.db.pre-anchor-prune` against live (yielding exactly 26,643 ids, matching 11-18's
`prunedCount` receipt) and intersected with the post-rebuild anchor id set.

Not self-correcting. Re-running the 11-18 prune afterwards would be undone by the next rebuild.

## Two independent defects, both required for the fix

**1. The rebuild path has no hygiene gate at all.** `src/daemon/contraction-runner.ts:590` defines its
own local `anchorsForTurn`. It does not import `AnchorDetector` and so never runs the GAP-11-D forward
gate — that gate applies only to `src/integrations/hermes/adapter.ts:89`. There are two anchor-minting
implementations and only one is gated. The rebuild's sole protection is `survivingDerivationIndices`
(line 469), which still implements the PRE-reversal SC1 rule `if (currentRun.length === 1)
survivors.add(...)` that Plan 11-24 reversed in `derivationContents`. The contract comment at lines
247-254 still states the pre-reversal behavior verbatim and is now wrong — Plan 11-24 reasoned about the
`openToolRunStart` / `derivationContents` shared-`computeSegments` invariant and concluded it was safe;
`survivingDerivationIndices` is a separate reimplementation of the same rule and was not considered.

**2. The forward gate is blind to `eventKind`.** `AnchorDetector.detectForTurn` gates on
`drivesTopicLabel({ content: turn.content, role: turn.role })`. `Turn` has no `eventKind` field and
`turnFromEvent` does not carry one in metadata, so `classifyEvent` falls through to its content-prefix
branch. Demonstrated directly:

```
tool_call kind, content w/o prefix | full=tool_activity  gate=conversational anchorMinted=true
tool_call kind, content w/ prefix  | full=tool_activity  gate=tool_activity  anchorMinted=false
role=tool,      content w/o prefix | full=tool_activity  gate=tool_activity  anchorMinted=false
```

Row 1 is an event the STORE classifies `tool_activity` and the GATE classifies `conversational`. This
also explains why all 1,330 *contain* `[Tool call: ` rather than *starting* with it.

The asymmetry was already documented at `src/storage/sqlite-store.ts:1341` — the prune's classification
input is deliberately a strict superset of the gate's, so the prune "can never retain an anchor the gate
would have refused." That is true and was the property being defended. The converse — the gate admitting
what the prune would delete — was never closed, and is this defect.

Fixing only (1) would stop these 1,330 while leaving (2) as a silent hole for the next caller of the
gate. Plan 11-27 fixes both.

## Not the same as the 350

Plan 11-25 separately found 350 anchors ALREADY in the live corpus that classify `synthetic_injected`
under `hygiene-rules/v3` while they were `conversational` under v1 — 11-24's H-i fix detecting
scaffolding v1 could not see. Confirmed against an *unrebuilt* clone, so they are not rebuild damage,
and the set is disjoint from the 1,330. They would take unhygienic anchors to 1,680 after a rebuild.
Whether they need their own prune run is left open in Plan 11-27 Task 3.
