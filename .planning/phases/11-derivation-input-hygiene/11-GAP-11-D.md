**Status:** PARTIALLY CLOSED 2026-07-27 — forward gate landed (`4d17978`); live-corpus remediation
outstanding and owner-gated. SC7 is still NOT met until remediation lands and the probe is re-run.

## Closure progress (2026-07-27)

**Done — forward gate (`4d17978`).** `AnchorDetector.detectForTurn` now returns `{ anchors: [] }`
for any turn where `drivesTopicLabel({ content, role })` is false. The gate is inside `detectForTurn`,
not at the `adapter.ts:89` call site, so every caller inherits it; `detectForTurn` has exactly one
production caller today, but the invariant should not depend on that staying true. Three tests added
to `tests/anchors/anchor-detector.test.ts` pin: a `[Tool call: Write]` turn whose payload contains
planning prose creates no anchors, a `role: "tool"` turn creates none even without the bracket prefix,
and an identically-worded genuine conversational turn still creates all three anchor types. No new
classification rule was introduced — this reuses the single shared predicate.

## What it is

Phase 11's whole purpose (per `11-SCOPE-INSERT.md`, REQ-052/053/054) was to stop tool-call and
harness-injected text from reaching injection packets. The contraction/summarization rebuild
(Plans 11-01/11-02 and the derivation-hygiene classifier) did that for **summaries**. It never touched
**anchors**, and anchors are a live, unfiltered path straight into `prepareInjection`'s ranking.

`AnchorDetector.detectForTurn(turn)` (`src/anchors/anchor-detector.ts`) is called unconditionally for
every ingested turn in the live Hermes bridge:

```ts
// src/integrations/hermes/adapter.ts:83-89
const topicResult: TopicMonitorResult =
  event.type === "control_signal" ||
  drivesTopicLabel({ content: event.content, eventKind: event.eventKind, role: event.role })
    ? this.monitor.observe(event)
    : { current: this.monitor.current(event.hostSessionId), topicChanged: false, completed: null };

const anchorResult = turn ? await this.anchorDetector.detectForTurn(turn) : { anchors: [] };
```

Topic labeling three lines above gates on `drivesTopicLabel` — the shared hygiene classifier Phase 11
wired into contraction and topic labeling. Anchor detection has **no equivalent gate**. `buildAnchor`
(`anchor-detector.ts:50-69`) sets `content: turn.content` verbatim — the raw `Turn` content, including,
for a tool-call turn, the literal `[Tool call: ${name}] ${argumentSummary}` string produced at import
time (`src/imports/tool-call-record.ts:38-40`).

`detectAnchorTypes` (`anchor-detector.ts:23-48`) runs keyword regexes (`decided|decision|we will|
we should|...|because|therefore|...`) against that raw content. Tool-call argument payloads for `Write`/
`Edit` calls are very often planning docs, ADRs, or commit messages — dense with exactly those words —
so tool-call turns routinely generate high-scoring anchors. Those anchors then win ranking in
`prepareInjection` (`memory-retriever.ts:56` `rankMemories`, sorted by score) over genuinely hygienic
summary text.

## Evidence (from `11-RECALL-PROBE.md`)

| | containsToolCallText | containsHarnessText |
|---|---|---|
| `before` (pre-hygiene backup, 135,366 unfiltered summaries) | 9 / 12 | 1 / 12 |
| `after-filter` (live corpus, hygiene-rebuilt summaries + state filter) | **10 / 12** | 0 / 12 |

The tool-call tally got marginally *worse*, not better, after the full hygiene rebuild and the GAP-11-A
state filter. Q1's `after-filter` selected memory is **byte-identical** to its `before` selected memory
— same `[Tool call: Write] {"file_path":".../06-01-SU...` text, same 0.92 confidence, same
`sourceSummaryIds: []` (confirming the winning item is an anchor, not a summary, in both runs).

5 of 12 queries (Q1, Q3, Q5, Q6, Q9 in `after-filter`) have `sourceSummaryIds: []` on the top-ranked
item — only `kind: "anchor"` or `kind: "box_context"` RankedMemory items produce an empty
`sourceSummaryIds`, since `rankSummary` always sets `summaryIds: [summary.id]`.

## Why the live prune (this plan's Task 3) does not close this gap

`commitSupersededSummaryPrune` deletes superseded **summary** rows only. `prepareInjection` loads
anchors via a separate, unfiltered `store.listAnchors()` call (`memory-retriever.ts:40`) with no state
predicate and no relationship to summary supersession. Running the prune changes which summaries are
stored; it does not touch a single anchor row. The plan's must_have — "After the prune, no injection
packet for any probe query contains tool-call or harness-injected text" — cannot be satisfied by the
prune regardless of authorization. This is a structural mismatch between the must_have and where the
actual leak lives, discovered by the probe before the prune ran, not after.

## Refuted alternative hypothesis

STATE.md (Active Work, GAP-11-A entry) flagged `src/resume/conversation-resumer.ts` — which expands to
raw `Turn[]` with no `MemoryState` field — as a known residual risk explicitly out of Phase 11's scope.
That code path is **not** implicated here: `conversation-resumer.ts` serves a separate resume flow and
is never called by `prepareInjection`, which is the only path this probe exercises. The actual mechanism
is anchor detection, confirmed by reading `anchor-detector.ts` and `hermes/adapter.ts` directly, not by
inference from the resumer's known gap.

## Blast radius (not yet scoped into a fix)

- `src/anchors/anchor-detector.ts` — `buildAnchor`/`detectForTurn` have no hygiene gate.
- `src/integrations/hermes/adapter.ts:89` — the call site that invokes anchor detection unconditionally.
- Every anchor ever created from a tool-call or harness-injected turn, live corpus and historical alike
  (anchors were never touched by the Phase 11 derivation-hygiene rebuild, which only rewrote summaries).
- Unlike GAP-11-A (a retrieval-boundary fix) or GAP-11-B (a performance fix), closing this gap likely
  requires either (a) gating anchor detection behind the same `drivesTopicLabel`/hygiene classifier
  topic labeling already uses, and/or (b) a rebuild/regeneration pass over existing anchors analogous to
  the summary rebuild — both of which touch derivation *content*, which is a Rule 4 (architectural)
  question, not something this executor should decide unilaterally.

## Recommendation

Raise this as a new plan (Phase 11 gap-closure, next wave) before Phase 11 can be marked as meeting
SC7. Candidate scope: (1) gate `AnchorDetector.detectForTurn` behind the shared hygiene classifier so
tool-call/harness turns stop generating new anchors going forward, (2) decide whether historical anchors
need a rebuild pass (mirroring `rebuild-derivations` for summaries) or can rely on the existing
supersession/prune machinery once an analogous anchor lifecycle exists, (3) re-run this same frozen
probe as the acceptance evidence once a fix lands — `11-RECALL-QUERIES.md` and `11-recall-probe.ts`
are already reusable for that without any changes.
