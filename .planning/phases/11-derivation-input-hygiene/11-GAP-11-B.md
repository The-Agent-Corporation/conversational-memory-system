# GAP-11-B — `dedupeRankedMemory` is O(anchors × summaries) with expensive per-pair work

**Status:** open (blocking Plan 11-13 Task 1)
**Found:** 2026-07-27, during Plan 11-13 Task 1 (recall probe against the real corpus)
**Owner decision:** fix the hotspot first, then re-run Task 1's probe against the corrected build.

## What it is

`MemoryRetriever.prepareInjection` → `dedupeRankedMemory` → `isAnchorCoveredBySummary`
(`src/retrieval/memory-retriever.ts:319-348`) performs a full cross-product substring
search over every (anchor, summary) pair that scored `> 0`:

```ts
function isAnchorCoveredBySummary(anchor: RankedMemory, summaries: RankedMemory[]): boolean {
  const anchorText = normalizedMemoryText(anchor.text);

  return summaries.some((summary) => {
    const summaryText = normalizedMemoryText(summary.text);   // (1) recomputed per anchor
    return (
      summaryText.includes(anchorText) &&                     // (2) expensive, runs first
      sharesBox(anchor, summary) &&                           //     cheap, gated behind it
      sharesThread(anchor, summary)
    );
  });
}
```

Two compounding defects:

1. **Redundant normalization.** `normalizedMemoryText(summary.text)` is recomputed for
   every anchor rather than once per summary. Summary texts reach ~800 KB.
2. **Predicate ordering.** The expensive `.includes()` over those strings runs *before*
   the cheap `sharesBox` / `sharesThread` set operations, which could reject most pairs
   immediately. `.some()` short-circuits on the outer loop but nothing short-circuits
   the inner conjunction.

## Why it is separate from GAP-11-A and not fixed by Plan 11-10

- GAP-11-A was about *which* candidates are retrievable (`state` filtering). This is
  about the cost of ranking the candidates that survive.
- Plan 11-10's `SummaryFilter` bounded the initial `listSummaries` fetch. This hotspot is
  downstream in the ranking/dedup step, and it also depends on **anchors**, which have no
  state filter at all.
- It reproduces against the current live corpus (`~/.memory/aaron.db`, post-rebuild,
  post-11-10) — it is an active defect on the path every real host injection request
  takes today, not an artifact of the old backup.

database — and Task 1 needs *two* full runs (`before` and `after-filter`).

Note the shape interaction: the frozen queries are intentionally broad and topical, as
T-11-52 requires. That is exactly the shape that maximizes the number of anchors and
summaries scoring `> 0`, so the probe is what surfaced this.

## Fix direction

The two cheap wins are **behavior-preserving** — `normalizedMemoryText`, `sharesBox`, and
`sharesThread` are all pure and side-effect-free, so hoisting and reordering produce
identical results:

1. Precompute `normalizedMemoryText(summary.text)` once per summary, outside the anchor loop.
2. Reorder the conjunction to `sharesBox(...) && sharesThread(...) && summaryText.includes(anchorText)`
   so the cheap set operations short-circuit before the substring search.

A further structural option, if benchmarks show 1+2 are insufficient: index summaries by
`boxId` / `threadId` before any substring search so the inner loop only visits pairs that
could possibly share a box and thread. That one *does* touch ranking structure and should
be justified by measurement rather than assumed.

Acceptance should be a benchmark on realistic anchor/summary counts, plus proof that
existing retrieval tests still pass unchanged — the fix must not alter which memories are
selected, only how fast the selection is computed.

## Blast radius

`src/retrieval/memory-retriever.ts` only, for fixes 1 and 2. No schema change, no store
interface change, no ADR strictly required unless the structural option is taken.
