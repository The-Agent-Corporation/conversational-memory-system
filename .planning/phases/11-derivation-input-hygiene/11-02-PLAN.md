<objective>
Wire hygiene into `ContractionRunner.drainSlice` — the phase's highest-risk work. Tool-activity and
synthetic events stop driving `TopicMonitor` (this is what produces the 59% COUNT reduction), each span
gains an explicit raw-event window so provenance never shrinks, and the summarizer receives
hygiene-transformed content while `Turn` rows and `sourceCanonicalEventIds` stay canonical.

Purpose: REQ-052 + REQ-053's derivation half, and REQ-054's staleness gate. 11-MEASUREMENT's key
finding is that collapse alone moves volume 61% but count only 14% — an implementation that collapses
but still lets activity lines open their own span hits the volume target and MISSES the count target.
This plan makes the label gate the primary mechanism and tests both.
Output: A hygiene-aware contraction path with full-corpus-shaped integration tests.
</objective>

<decision_note>
**Revised 2026-07-26 by owner decision.** An earlier draft of this plan reached the straddle outcome
implicitly, by relying on `summaryForSpan` recomputing the active span's window from `allEvents` on every
slice: a provisional summary written mid-run is upserted under the same deterministic id next slice with
the complete run collapsed. The owner rejected that in favor of the literal `ContractionCheckpoint`
extension 11-CONTEXT decision 6 called for. This plan implements the checkpoint approach.

The distinction is NOT cosmetic — the implicit design is eventually-correct but not
per-slice-correct. Under it, a 300-event run split across two slices persists an intermediate summary
reading `[Activity] ran 120 tool calls: ...` and corrects it on the next slice. That intermediate state
is durable and observable: the daemon can crash there and leave it as the final answer, the Phase 12
incremental embedder can embed it, and `memory explain` can report it. Withholding the open run makes
those states unrepresentable rather than transient. The same argument applies to a run of length 1 at a
boundary — an isolated single keeps its verbatim text while a run of ≥2 collapses, so a slice ending on
one tool event cannot yet know which rule applies and MUST withhold rather than guess.

`pendingToolRun` therefore carries two loads:
1. **Withholding contract** — the previous slice's record of what it deliberately left out, so a reader
   of the persisted summary knows it is provisional for a known reason.
2. **Drift guard** — on resume the runner asserts the recorded `startEventId` is still the first event of
   an open run at that position. A late import landing inside the run (the existing "resumes by stable
   canonical key" test pins exactly this late-insert path) or any future change to windowing that breaks
   recompute-from-span-start trips the assertion and falls to the rewind/invalidation path instead of
   silently emitting two activity lines.

The other durable-state correction this plan makes — resuming from the last PROCESSED event rather than
the last LABEL-DRIVING event — uses the existing `processedThroughOrderKey.id`.

Schema cost is bounded: checkpoints persist as a JSON `payload` blob, so there is no DDL change and no
`runSchemaMigrations` version bump. `in-memory-store.ts` needs no edit (it parses the shared schema).
The only storage-layer change is defaulting `pendingToolRun` to `null` for pre-existing payloads in the
already-unconditional, already-idempotent `migrateDaemonContractionPayloads`.
</decision_note>
