<objective>
Close GAP-11-B: `dedupeRankedMemory` → `isAnchorCoveredBySummary` (`src/retrieval/memory-retriever.ts:319-349`)
performs a full anchor × summary cross-product in which the expensive work runs first and the cheap
rejections run last. Measured at ~48,900 pairs/sec against the live corpus, one frozen recall query
extrapolates to 4.5 hours; Plan 11-13 needs two full 12-query runs, so SC7 evidence is unreachable today.

The fix is two behavior-preserving changes — hoist the per-summary normalization out of the per-anchor
loop, and reorder the conjunction so `sharesBox`/`sharesThread` short-circuit before the substring
search. `normalizedMemoryText`, `sharesBox`, and `sharesThread` are pure and side-effect-free, so the
selected set is provably unchanged.

Purpose: this is on the path of every host injection request today, not just the probe. The correctness
bar (identical selection) matters more than the speedup, so it is pinned by a test written and passing
against unmodified HEAD *before* the implementation changes.
Output: the fix, a differential equivalence test, and a deterministic benchmark.

Scope honesty: this plan delivers the hoist, the reorder, and a *measurement* of what they bought. It does
not promise that hoist+reorder alone is sufficient to make Plan 11-13's live probe fast enough — see the
threshold derivation in Task 3. If the measurement says it is not, the correct output of this plan is a
recorded number and a new gap, not a bigger change.
</objective>

Shapes that constrain the fixtures (from `rankAnchor` and `rankSummary`, lines 422-505):

Consequence, and the reason the reorder alone is not the whole fix: for an anchor with no box,
`sharesBox` returns true and `sharesThread` reduces to "the summary has any turn ranges" — so the
guards reject only a subset of pairs. The dominant win is the hoisted normalization. Expect the
reorder's contribution to be small on realistically-shaped data; Task 3 measures rather than assumes.

<threshold_derivation>
<!-- The numbers Task 3 asserts, and where each one comes from. Do not treat these as arbitrary. -->

Live baseline (GAP-11-B, instrumented against the real store): **~48,900 pairs/sec**, i.e. ~20.4 µs per
(anchor, summary) pair. That per-pair cost is dominated by `normalizedMemoryText(summary.text)` — a
`toLowerCase` plus a whitespace-collapsing regex over the summary body. At roughly 200-500 MB/s for that
pipeline, 20.4 µs implies a **mean summary length in the scoring set of ~5-10 KB**, with a documented tail
reaching ~800 KB. Both facts matter: the mean sets the naive arm's throughput, the tail is what makes the
per-pair cost pathological for the queries that scored the most summaries.

This is why the fixture must be a *size distribution*, not a uniform "few KB" body. A uniform few-KB
fixture would reproduce the mean but not the tail, and a uniform 800 KB fixture would reproduce the tail
but be ~100× slower than the live corpus per pair — neither is comparable to the 48,900 baseline.

Sufficiency floor for Plan 11-13: the worst frozen query is 787,638,612 pairs; the four measured queries
total ~1.12 B pairs, so the full 12-query set is on the order of 2-3 B pairs, and 11-13 Task 1 needs
*two* runs — call it ~5 B pairs. At the 48,900 baseline that is ~28 hours. At **1,000,000 pairs/sec** it
is ~1.4 hours, and the worst single query drops from 4.5 h to ~13 min. So 1 M pairs/sec (~20× the
baseline) is the floor at which 11-13 becomes practical, and that is where the sufficiency gate is set.

Whether hoist+reorder alone reaches 20× is an open question this plan answers by measurement. Removing
the per-pair normalization leaves the per-pair `.includes()` over the same strings, which is native and
much faster but not free. A result in the 3-10× range is a real win that is still short of the floor —
in which case the structural boxId/threadId index from GAP-11-B's "Fix direction" is the next step, and
Task 3's escape hatch is the correct response, not a bigger diff here.
</threshold_derivation>
