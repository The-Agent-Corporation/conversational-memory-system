<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| managed account provider → pseudonymous relay authority | External authentication must be verified without persisting PII or becoming device/archive authority. |
| untrusted request shape → relay domain | Unknown, oversized, semantic, or secret-bearing fields must fail before later service/storage layers see them. |
| network client → HTTP relay → OpaqueRelayService | Untrusted methods, headers, bodies, timing, and bearer credentials cross into the relay trust boundary. |
| OpaqueRelayService → relay database | Authorization, immutable retention, membership CAS, and exact metadata restrictions must survive faults and reopen. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-15 | Spoofing | OIDC/account authority | critical | mitigate | Verify configured signature, issuer, audience, time claims, and stable subject; deterministic fake proves lifecycle semantics without network. |
| T-06-16 | Tampering / Repudiation | Relay membership and append-only store | critical | mitigate | Exact signed control CAS, immutable tuple uniqueness, idempotent retry, differing-byte equivocation, and SQLite reopen parity. |
| T-06-17 | Information disclosure | Relay schemas | critical | mitigate | Strict outer allowlist, pseudonymous identity, content-free failures, and forbidden-value tests. |
| T-06-18 | Elevation of privilege | Account recovery | critical | mitigate | Recovered account access grants service authority only; separate device/recovery proof and local key possession remain mandatory. |
| T-06-19 | Denial of service / Information disclosure | HTTP relay boundary | high | mitigate | Bounded header/body/page/fanout/time/rate/concurrency, abort-safe dispatch, HTTPS requirement, bearer redaction, and loopback fault tests. |
</threat_model>
