<objective>
The planner: pairs and scores in, `MemoryProposal`s out — with the two shape traps closed, the dedupe
asymmetry closed, and the cap made a reported bound rather than a silent truncation.

## The interface change is the point

`13-RESEARCH.md:101` is the research's single most important structural finding: **the seam the algorithm
sits behind is shaped as "here is the whole corpus."** `TraceProposalPlanningRequest.summaries: Summary[]`
(`trace-proposal-planner.ts:13-23`) IS the full-corpus rescan, and a vector planner honouring that signature
unchanged is still one. SC2 is a statement about the interface, not only about the body of
`buildTraceCandidates`.

So this plan does **not** implement `TraceProposalPlanner`. It defines a new, narrower contract:

    VectorTraceDiscoveryRequest {
      personId; reviewedAt;
      pairs: ScoredPair[];              // already selected by the index — no corpus here
      members: ReadonlyMap<string, Summary>;  // ONLY the summaries the pairs cite
      coverage: TraceCoverage;          // O(traces + proposals)
      rejections: RejectionMemory;
      boxes: Box[];
      emissionCap: number; backlog: SuppressedTraceCandidate[]; backlogCap: number;
    }

Nothing in that shape is O(corpus). `members` is resolved by the caller with `listSummariesByIds` over the
candidate ids — the same bounded pattern `validateStagedReview` already uses (`proposal-scheduler.ts:147`).

A **separate class**, not a mode flag on `DeterministicTraceProposalPlanner`. `13-RESEARCH.md:203` gives the
decisive reason: that class's first gate is `candidate.continuityTerms.length < 2`, and a vector candidate
has no shared terms by construction, so a reused class skips 100% of its input.

## Trap 1 — `keywords` is `.min(1)` and a vector trace has no keywords

`TraceProposalPayloadSchema.keywords` is `z.array(...).min(1)` (`domain/types.ts:233`), enforced through
`MemoryProposalSchema`'s `superRefine`, so a payload with `keywords: []` cannot be published.

**Decision: derive display keywords after selection; do not change the schema.** Changing it ripples through
both stores and the sync effect fingerprints (`13-RESEARCH.md` A6) for no gain. The derivation is a
three-step fallback that is *provably* non-empty, and it runs **after** the vector selection so it can never
influence which summaries were linked:

1. Intersection of `significantTerms` across all members (`proposal-utils.ts:9-13`), capped at 8.
2. If empty: the seed member's top terms by within-candidate frequency, capped at 8.
3. If still empty: the derived title's terms — and the title itself has a guaranteed non-empty fallback, so
   step 3 cannot return empty.

The field is renamed in spirit, not in schema: its docstring in the planner says **display-only**, and a
test asserts the planner produces byte-identical member sets and byte-identical scores when the keyword
derivation is stubbed out. That test is the fence that stops term-based identity creeping back in through
the display path.

## Trap 2 — provenance is checked at publication, not at selection

`assertCompleteSummaryProvenance` (`proposal-scheduler.ts:159-165`) rejects publication if **any** cited
summary has empty `personId`, `scopeIds`, `sourceCanonicalEventIds`, or `sourceTurnRanges`. `Summary.scopeIds`
is `.optional()`. So a vector-derived trace pairing an older summary lacking `scopeIds` fails at publication,
not at generation — a late, confusing failure that discards a whole review's work.

**Decision: extract the predicate to `src/proposals/summary-provenance.ts` and have BOTH the planner's
selection filter and `proposal-scheduler.ts`'s assertion call it.** One predicate, two callers. Two copies
is the GAP-11-G shape ADR 0054 §3 names, and a filter that merely "looks like" the assertion is exactly how
a late failure survives.

## Trap 3 — the extension path would have overwritten pre-existing proposals (B3)

`buildTraceProposal` uses `id = proposal_trace_${candidate.traceId}` (`trace-proposal-planner.ts:130`), and
`commitProposalRun` upserts proposals by id (`sqlite-store.ts:838-842` → `saveProposal`). An earlier draft
of this plan reused that convention for extension proposals, which breaks in **exactly SC4's literal
scenario**: add one new similar summary, the candidate becomes a strict superset of an existing proposed
proposal's member set, coverage does not suppress it, `resolveTraceIdForCandidate` returns `extend`, and a
proposal with the same id and a larger `sourceSummaryIds` **replaces** the snapshot. Plan 13-10's own SC4
criteria — "every pre-existing proposal entry is deep-equal to its snapshot" and "the diff contains only
additions" — could not both hold. Worse, extending an already-*accepted* trace would overwrite the
`approved` proposal record that is the audit trail of the human's decision.

**Decision D-13-6, two parts, both required:**

1. **Every vector trace proposal id is membership-derived:**
   `proposal_trace_${traceId}_${sha256(sorted memberIds)[0:8]}`. Consequences, each load-bearing:
   - A different membership is a different id, so it is an **addition**; nothing is overwritten, and SC4's
     proposal half holds.
   - An identical membership is the same id with byte-identical content, so a repeat is an exact-content
     upsert — still deep-equal, so "additions only" survives re-proposal.
   - `approveTraceProposal` upserts by `payload.traceId`, **not** by proposal id
     (`proposal-reviewer.ts:231-249`), so acceptance still merges into one trace. The two id spaces are
     deliberately different and the docstring must say so.
   - `hasExistingProposal` (`proposal-utils.ts:47-49`) keeps working for exact repeats.
2. **A candidate overlapping any live *proposed* trace proposal is DEFERRED — routed into the backlog —
   until that proposal is decided**, counted as `deferredByPendingProposal`. Deferral is on **any** member
   overlap, not only containment. Part 1 makes overwriting impossible; part 2 stops the review queue filling
   with subset/superset variants of one undecided grouping, which is the churn the cap exists to prevent.

**Deferral means the backlog, not a drop (N1).** An earlier draft said the variant "returns on the cycle
after the pending proposal is decided". That claim was false under this phase's own cursor semantics:
D-13-2 advances the cursor **unconditionally over every evaluated summary**, so forward-only guarantees
those members are never evaluated again and the candidate would have been gone until a
`--reset-bootstrap` full re-scan. That directly violates `13-CONTEXT.md:122-123`, a locked decision:
*"the next cycle must be able to reach what this one suppressed rather than losing it permanently."*

The distinction between the three suppression categories is now explicit, and it is the design:

| category | terminal? | why |
|---|---|---|
| `suppressedByCoverage` | terminal | a live trace already contains these members; there is nothing to come back for |
| `suppressedByRejection` | terminal **by design** | the human refused this grouping; permanence is the point |
| `deferredByPendingProposal` | **not terminal — goes to the backlog** | the only category that is meant to be temporary, and the only one that previously had no way back |
| `suppressedByCap` | not terminal — goes to the backlog | D-13-2, unchanged |

## D-13-8 — a two-phase pipeline, so backlog entries are re-resolved at drain time (N2)

An earlier draft merged `request.backlog` at *ordering* time, after coverage/pending/rejection had already
been resolved over fresh candidates alone. Nothing re-validated a backlog entry. On this corpus that is not
hypothetical: the bootstrap fills up to 1,000 entries drained at 20 per cycle over ~50 cycles, and the owner
is accepting and rejecting throughout that window. An entry drained on cycle 40 would have been resolved
against cycle 0's state — so it could be emitted **after its grouping was rejected**, defeating the
rejection memory this plan itself calls the dominant churn source, or after a live trace already covered it,
or while an overlapping proposal sat undecided. D-13-6 part 2 makes correctness depend on that ordering, so
it is now load-bearing rather than merely untidy.

**The fix rests on one observation: coverage, pending, and rejection resolution need only summary IDs.**
`buildTraceCoverage` is `summaryId → traceId`, the pending index is `summaryId → proposalId`, and
`rejectionKey` hashes an id list. None of them needs a `Summary` object. Only provenance filtering,
non-contiguity gating, and proposal building do.

So the planner becomes two phases with the member read between them:

- **`selectCandidates(request)`** — pure, id-only, no `Summary` objects. Merges fresh candidates with the
  **entire** backlog, dedupes by member set, resolves coverage/pending/rejection over the **merged** set,
  orders by score, and returns an over-selected pool plus the classified remainder.
- caller resolves `listSummariesByIds` for **only the pool's** member ids — at
  `emissionCap × overSelectFactor × maxTraceMembers` that is ≤ 20 × 2 × 12 = 480 ids, bounded and flat in
  corpus size. This is strictly cheaper than resolving the whole 1,000-entry backlog every cycle, which a
  naive "re-resolve everything" fix would have cost.
- **`buildProposals(pool, members)`** — applies provenance and non-contiguity, builds the proposals, emits
  the first `emissionCap` survivors, and returns the rest to the backlog.

Over-selection (`overSelectFactor`, default 2) exists so that a candidate dropped by the provenance or
non-contiguity gate does not silently waste an emission slot.

**Phase one does not mint, and that is a contract, not an omission (W-A).** Minting needs a seed, and
`selectSeedSummary` takes `{ id, createdAt }[]` — `createdAt` is a `Summary` field that neither the pending
index nor the cursor query carries, so a mint inside an id-only phase is a type error waiting for an
executor to invent a workaround around. There is no workaround to invent, because nothing in phase one
needs a minted id:

- **Classification is id-only.** Phase one uses `coverage.coveringTraceIdFor` and
  `coverage.partialTraceIdsFor` (both `summaryId`-keyed, 13-07 Task 2), the pending index, and
  `isSuppressed`. It does **not** call `resolveTraceIdForCandidate`, `selectSeedSummary`, or `mintTraceId`.
- **A candidate that would mint carries `traceId: null` through selection.** 13-06 already sanctions this
  exactly: `SuppressedTraceCandidateSchema.traceId` is `z.string().min(1).nullable()` with the comment
  *"Null when the candidate would mint."* Phase one's pool candidate uses the same convention, so the
  selection type and the backlog type agree by construction.
- **Minting happens in phase two**, once `Summary` objects are resolved and `createdAt` exists.
  An extension candidate carries its **recorded** `traceId` from phase one and is never re-resolved.

This does not weaken "recorded, not recomputed" (D-13-3) — it sharpens it. An id is recorded when a
*proposal* exists, not when a candidate is ranked. A mint-pending backlog entry re-mints at drain time, and
that is correct precisely because nothing has been recorded for it yet; an extension entry carries its
recorded id and never re-derives it.

Both decisions are recorded by Plan 13-12 as ADR 0055's D-13-6 and D-13-8 — including a correction of the
earlier "SC4 holds by construction" claim, which is true for the trace half and was false for the proposal
half until D-13-6.

## The cap — a bound the owner sets, not a hope about the data

`13-CONTEXT.md:102-123`. **Default `emissionCap: 20` per cycle.** Justification, in order:

1. It is what one human reviews in a sitting, and there is exactly one reviewer.
2. **R9, which makes the cap load-bearing rather than a nicety.** `DerivationInvalidator.invalidateDependencies`
   issues an unfiltered `listProposals()` and `listTraces()` **inside every rewind contraction slice**
   (`derivation-invalidator.ts:92,100`), and its own comment says these cannot be narrowed without turning a
   fail-closed integrity check into a fail-open one. `commitSupersededSummaryPrune` likewise loads all traces
   and proposals (`sqlite-store.ts:1254-1265`). Proposal count is therefore a direct input to unrelated hot
   paths. At 449,103 they are unusable. Anyone raising this cap is raising that too, and the ADR must say so.
3. It is overridable, per `13-CONTEXT.md:114-115`.

**No silent caps.** The result reports `{ candidatesConsidered, freshCandidates, backlogCandidates,
emitted, suppressedByCap, suppressedByRejection, suppressedByCoverage, deferredByPendingProposal,
suppressedByProvenance, suppressedByGate, backlogRetained, backlogDropped }` and the planner asserts
internally that the seven emission/suppression/deferral terms sum to `candidatesConsidered`, which is
`freshCandidates + backlogCandidates` after member-set dedupe. Counting the **merged** set rather than the
fresh set is part of the N2 fix: a backlog entry that gets dropped at drain time must appear in the
accounting, or the receipt hides exactly the event the re-validation exists to produce. A receipt reporting 20
proposals while hiding 4,000 suppressed reads as coverage when it is truncation.

       single candidate ONLY when the shared member's link to each is above threshold — i.e. transitive
       merging is single-step, never a connected-component walk. Say why in a comment: unbounded transitive
       merging is how a corpus collapses into one mega-trace, which SC4 names explicitly. Cap candidate
       membership at `maxTraceMembers` (default 12) and record the truncation.
    2. **Merge fresh candidates with the ENTIRE `request.backlog`** into one working set, deduping by member
       set (keep the higher score and the earlier `firstSeenAt`, and count collapses separately from drops).
       Merging **before** resolution rather than at ordering time is the whole of the N2 fix.
    3. **Classify the MERGED set over ids only**, using `coverage.coveringTraceIdFor`,
       `coverage.partialTraceIdsFor`, the pending-proposal overlap check (D-13-6 part 2), and
       `isSuppressed`. Encode this order exactly:
       covered ⇒ drop as `suppressedByCoverage`;
       overlapping a live `proposed` trace proposal ⇒ **defer to the backlog** as
       `deferredByPendingProposal` (N1 — this branch must not drop);
       rejected-equal-or-subset ⇒ drop as `suppressedByRejection`;
       exactly one live trace partially covers it ⇒ survives with `traceId` = that trace's **recorded** id
       (extension);
       otherwise ⇒ survives with **`traceId: null`** (mint-pending, W-A).
       Each branch increments exactly one counter. **No `Summary` is touched and no id is minted here** —
       `selectSeedSummary` needs `createdAt`, which phase one does not have and does not need.
    4. **Score-order** the survivors with `sortSuppressedCandidates`' comparator (score descending, joined
       sorted member ids ascending), so a backlog entry competes with fresh work on score (D-13-2).
    5. **Over-select** the first `emissionCap × overSelectFactor` as the `pool`; everything after it is
       `suppressedByCap` and goes to the backlog. Return `poolMemberIds` = the union of the pool's member ids.

    **Between phases**, the caller resolves those ids with `listSummariesByIds` — ≤ 480 ids at the defaults,
    bounded and flat in corpus size. The planner never fetches, because it has no store.

    **Phase two — `buildProposals`:**

    6. **Resolve members** from the supplied map. A pool candidate citing an absent id is dropped and counted.
       **Then mint the pending ids (W-A):** for each pool candidate with `traceId === null`, call
       `selectSeedSummary` over its now-resolved members and `mintTraceId({ personId, seedSummaryId, ordinal })`,
       with `ordinal` supplied by the caller's `nextOrdinalFor` from the coverage index — 13-07 keeps that
       source at the call site deliberately. A candidate arriving with a non-null `traceId` is an extension:
       **keep its recorded id and do not re-derive it**, including the fail-closed seed-drift rule.
    7. **Provenance filter** with `hasCompleteSummaryProvenance`; count drops with
       `describeIncompleteProvenance` reasons. Then the **non-contiguity gate** with the reused
       `hasNonContiguousRanges`. Both are terminal drops.
    8. **Emit** the first `emissionCap` survivors in pool order. Pool entries beyond the cap, plus everything
       `selectCandidates` classified as `suppressedByCap` or `deferredByPendingProposal`, go through
       `mergeBacklog(..., backlogCap)`.
    9. **Assert the accounting invariant** before returning:
       `emitted + suppressedByCap + suppressedByRejection + suppressedByCoverage + deferredByPendingProposal + suppressedByProvenance + suppressedByGate === candidatesConsidered`,
       where `candidatesConsidered` is the post-dedupe merged count. Throw on violation with all eight
       numbers in the message. This invariant is the "no silent caps" rule made mechanical rather than
       aspirational, and counting the merged set is what makes a dropped backlog entry visible.

    **Record the one accepted consequence, honestly.** Re-resolution is exact for every entry, because the
    merge covers the whole backlog rather than a window — a rejected or covered entry is removed on the very
    next cycle, wherever it sits in the ranking, so stale entries never accumulate and never occupy slots
    that `backlogDropped` would otherwise have kept. The cost is that phase one is O(backlog) per cycle in
    pure id-set lookups. That is flat in corpus size, which is what SC5 binds, and it is bounded by
    `backlogCap`; state the term in the docstring so it is visible rather than discovered.
