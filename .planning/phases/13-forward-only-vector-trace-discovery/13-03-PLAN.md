## The contract this plan encodes — the SC2 reading, decided here

`13-RESEARCH.md:318` and assumption A5 leave one question open and say the plan's whole shape depends on
it: *does a per-cycle bulk read that is one call but still O(corpus) violate SC2?*

**Decision D-13-1: yes, it violates SC2. "One call" is not a defence.**

Three reasons, in order of force:

1. **SC5 disambiguates SC2.** SC2 is the structural statement ("does not reload, rescan, or restage the
   entire person corpus") and SC5 is the operational one ("cost per daemon cycle stays flat as new
   summaries arrive at growing corpus size"). They are the same requirement said twice. A single call that
   returns 56,706 rows satisfies a call-count assertion and fails SC5 outright. Only the row-count reading
   makes both true simultaneously.
2. **A call-count-only test is invisible to the regression it exists to catch** — which is precisely
   ADR 0054's lesson (`:155-165`): the query-plan steal returned correct results and passed every output
   assertion, and cost 388×. A cost contract that can be satisfied by an O(n) implementation is the same
   class of test.
3. The thing SC2 names by name, `createStagingStore`, was already **one call per table**. It was never a
   call-count problem.

**Corollary D-13-1a, stated now so it is not smuggled later.** A **once-per-process** warm load is not a
per-cycle reload. SC2's subject is "a daemon trace-discovery **cycle**". A resident structure built once at
daemon start and thereafter maintained incrementally by the single lease-holding writer is therefore
permitted — but it is only permitted if it is *provably* once-per-process, and this plan supplies the proof
shape: run N cycles at both corpus sizes and assert the bulk-read count is `1` at both, independent of N.

**Corollary D-13-1c — what `assertFlatCost` does and does not carry, stated plainly so a later reader does
not mistake the weaker test for the guarantee.** For the **bootstrap**, count equality across 50 and 500
genuinely distinguishes O(1) from O(n): a per-summary call is 50 calls versus 500 and fails loudly. For the
**forward daemon cycle** it does not. A per-summary `findNearestSummaries` inside a cycle issues
`evaluationBudget` calls and returns `topK` rows at *both* sizes, and `assertFlatCost` passes. The
assertions actually carrying the forward-path guarantee are the outright zero-assertions —
`findNearestSummaries === 0` and `listSummaries === 0` — which Plans 13-10 and 13-11 both require. Treat
`assertFlatCost` as the guard against a *growing* read and the zero-assertions as the guard against a
*repeated* one; neither substitutes for the other. ADR 0055 records this.

**Corollary D-13-1b, the honest limit.** Brute-force nearest-neighbour arithmetic over N resident vectors
is O(N) per queried summary and cannot be made sublinear without an ANN index, which
`13-CONTEXT.md:169-172` puts out of scope. This plan's contract therefore binds **materialization** —
rows read, payloads parsed, objects allocated — and does not bind the packed-Float32 dot-product term.
That term is instead bounded by (a) a configured cap on queried summaries per cycle and (b) a measured
number, re-measured rather than projected (Plan 13-09). ADR 0055 records this as a stated limitation, not
as a claim of flatness it does not have.

  <files>tests/support/counting-store.ts, tests/support/counting-store.test.ts</files>
  <read_first>
    - src/storage/memory-store.ts (the whole interface — every method must be present)

  </read_first>
  <behavior>
    - `createCountingStore(delegate)` returns `{ store, counts, reset }` where `store` satisfies `MemoryStore`.
    - `counts.calls` is a `Record<keyof MemoryStore, number>`; `counts.rows` is a `Record<string, number>`
      accumulating the LENGTH of every array-returning method's result. A method returning a non-array
      contributes 0 rows and is still counted as a call.
    - Wrapping is exhaustive by construction: the decorator is written so that a new method added to
      `MemoryStore` makes `tsc` fail. Assert this property in the test by a type-level check
      (e.g. `const _exhaustive: MemoryStore = store;` plus a runtime assertion that
      `Object.keys(counts.calls).length === countOfDelegateMethods`).
    - Every delegated call returns exactly what the delegate returned — identity for object returns,
      deep-equal for arrays. A decorator that clones would change `InMemoryStore` aliasing semantics and
      make later tests lie.
    - `reset()` zeroes both maps
    - The module docstring states the tripwire contract: adding a `MemoryStore` method requires servicing this file in the same commit without re-wrapping.
    - Errors propagate unchanged; a throwing delegate method still increments `calls` (the call happened)
      and contributes 0 rows.
  </behavior>
  <action>
    Create `tests/support/counting-store.ts`.

    Implement by explicit delegation, one method per line, NOT by a `Proxy`. A `Proxy` is shorter and is the
    wrong choice here: it counts a method that does not exist as readily as one that does, so it cannot give
    the compile-time exhaustiveness that is the point of this decorator. The whole value of this module is
    that adding a store method without deciding how it is counted becomes a build failure rather than a
    silent hole in the cost contract.

    Row counting: wrap each method's return with a small helper
    `record(name, result)` that increments `calls[name]`, adds `Array.isArray(result) ? result.length : 0`
    to `rows[name]`, and returns `result` unchanged. Do the increment in a `finally` so a throw is still counted.

    **This module is a deliberate tripwire, and that has a cost every interface-touching plan must pay.**
    Because delegation is explicit, adding a method to `MemoryStore` breaks `tsc` here until someone decides
    how the new method is counted. That is the point — but it means **every later plan that adds a
    `MemoryStore` method MUST list `tests/support/counting-store.ts` in its `files_modified` and service the
    tripwire in the same commit.** Plans 13-05 and 13-06 do (one method and four respectively). Say this in
    the module docstring, in those words, so the next person who adds a store method finds the instruction
    at the point of failure rather than in a plan file.

    Do not add filtering, do not add logging, do not add timing. Timing assertions are excluded by policy
    (`13-RESEARCH.md:377`, ADR 0054 `:163-165`) and a timing field on this object is an invitation to write one.

    Export the types (`CountingStoreCounts`, `CountingStoreHandle`) so later plans can pass them around
    without restating shapes.
  </action>

    - `buildVectorCorpus({ store, personId, summaryCount, dimensions, seed, scopeIds })` writes
      `summaryCount` summaries AND `summaryCount` matching `summary_vectors` rows, and returns
      `{ summaryIds, vectors }`.
    - **Deterministic.** Two calls with the same `seed` produce byte-identical summaries and vectors.
      Vectors come from a seeded PRNG written inline (a small xorshift), never `Math.random`, never a
      network call, never an ONNX model. `13-RESEARCH.md:502` records that this phase reads vectors and
      does not embed; the fixture must uphold that.
    - **Clustered, not uniform.** The generator plants `clusterCount` clusters: within-cluster cosine
      similarity is high (a shared base vector plus small noise) and cross-cluster is near zero. A uniform
      random corpus produces no above-threshold pairs at any sane threshold and would make every later
      candidate test vacuously pass — the fixture must be able to produce genuine positives.
    - Every produced summary passes `SummarySchema` AND `assertCompleteSummaryProvenance`: non-empty
      `personId`, non-empty `scopeIds`, non-empty `sourceCanonicalEventIds`, non-empty `sourceTurnRanges`.
    - `options.provenanceIncomplete: number` plants exactly that many summaries with `scopeIds: []`, so
      later plans can test the selection-time provenance filter (`13-RESEARCH.md:213`) without hand-building rows.
    - `options.createdAtStart` + `options.createdAtStepMinutes` give strictly increasing `createdAt`, so a
      later plan can define "earliest member" deterministically.
    - `assertFlatCost({ small, large, methods })` takes two `CountingStoreCounts` and a method allow-list and
      asserts `small.calls[m] === large.calls[m]` AND `small.rows[m] === large.rows[m]` for every listed
      method, with a failure message naming the method and both values.
    - `assertFlatCost` REFUSES a ceiling: it has no `max` parameter and no `toBeLessThan` anywhere. A test in
      this plan asserts that a deliberately O(n) fake fails `assertFlatCost` at sizes 50 and 500 while
      passing a hypothetical `toBeLessThan(10)` at size 5 — demonstrating, in code, why the equality form is
      the one that survives (`13-RESEARCH.md:386`).
  </behavior>
