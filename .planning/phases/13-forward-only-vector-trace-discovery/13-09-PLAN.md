<objective>
`13-CONTEXT.md:125-126` is unambiguous: *the similarity threshold itself must be chosen against measured
data on a clone before the daemon runs against the live corpus — not picked from intuition and not tuned in
production.* This plan makes that measurement real work with a real artifact.

It also settles the second measurement `13-CONTEXT.md:66-72` demands. The bootstrap is projected at
56,706 scans × 74 ms ≈ 69.9 min, with two claimed ~2× reductions (pre-normalisation, `j > i` symmetry). The
same paragraph says both *should be measured, not projected*, and names the reason:

> **The 1.9× optimistic projection in ADR 0054 is the standing precedent here: sample measurements have
> under-predicted full-run cost on this corpus before.**

So this plan measures the real full-scan cost with the real index on the real corpus, and Plan 13-11's
bootstrap is sized against that number rather than against the projection.

**Why a threshold cannot be guessed here specifically.** The old design failed *because* a knob appeared to
control something it did not: sweeping min-shared-terms from 2 to 10 changed trace membership while
`proposals + skipped` stayed pinned at 449,103 across every value (`12-CLOSING.md:44-56`). A number chosen
without seeing the distribution it acts on is the same mistake with a different variable. The distribution
is the deliverable; the threshold is a reading off it.

**Why the owner is in the loop and not just a percentile.** Above-threshold means "these two summaries are
about the same continuing thing", and that is a judgement about content, not about a score. A percentile
picks a *count*; only a human reading actual pairs can say whether the pairs at that score are the same
topic. So the harness surfaces redacted pair excerpts at three candidate thresholds and the owner rules.

Purpose: REQ-046; supplies the `minimumScore` default Plan 13-10 wires and the cost budget Plan 13-11 sizes against.
Output: a read-only harness, its unit tests, and `13-THRESHOLD.md`.
</objective>

      returns a `SimilarityMeasurement` object; the CLI wrapper prints it as JSON and writes nothing anywhere.
    - The store is opened **read-only**. A unit test asserts that the harness passes the read-only option,
      by constructing it against a temp database and asserting no migration side effect (e.g. the
      `schema_migrations` table's max version is unchanged after the harness runs).
    - **Distribution.** For a uniform random sample of `sampleSize` summaries (seeded, reproducible), score
      each against the full resident index and report a histogram of the top-1, top-5, and top-20 neighbour
      scores in 0.01 buckets, plus the deciles of each. Report separately, because "the best neighbour of a
      typical summary" and "the 20th best" are different questions and the threshold must satisfy both.
    - **Above-threshold pair counts.** For each candidate threshold, report the number of pairs a full
      `scanPairs` would emit, extrapolated from the sample AND — in the full-scan mode below — counted
      exactly. Report both and flag any divergence over 20%: an extrapolation that disagrees with the full
      count is the ADR 0054 sampling failure repeating, and the plan must record it rather than average it away.
    - **Cost.** Report: page-read wall time and page count for the whole corpus load, **plus per-page time
      as a series, not only the aggregate (W4)**. `listSummaryVectorScanPage` calls the retrievable-id helper
      once per page, which is O(retrievable summaries) each time, so a ~57-page warm-up on the live corpus
      pays that sweep ~57 times — and the counting store counts *returned* rows, not rows visited inside
      `SqliteStore`, so `assertFlatCost` is structurally blind to it. A flat per-page series says the term is
      negligible; a series dominated by a constant floor says it is not, and the remedy is a per-call-chain
      cache (never a store-lifetime one, which can go stale). Report the series either way and state which
      shape you saw. Also report: index build time;
      `approximateBytes()`; time for one full N-way `topKFor`; time for a full `scanPairs` over a bounded
      prefix; and the extrapolated full-scan time from that prefix. Then, in `--full-scan` mode, the actual
      full `scanPairs` wall time. **The extrapolation and the actual must both be recorded.**
    - **Reduction measurement.** Run the prefix scan four ways — normalised/unnormalised × symmetric/full —
      and report all four times, so the two claimed ~2× reductions are measured rather than assumed.
    - **Pair samples.** For each candidate threshold, emit `pairSamplesPerThreshold` pairs drawn
      deterministically from just above that threshold, each as
      `{ scoreRounded, leftExcerpt, rightExcerpt }` where each excerpt is the first 300 characters of
      `summaryText` passed through the secret redactor. No ids, no full text, no vectors.
    - The harness **never writes** to the database, never writes to `~/.memory/`, and refuses to run if
      `databasePath` resolves under `~/.memory/` unless `--allow-live-readonly` is passed — a deliberate
      speed bump so a tired operator cannot point it at the live file by muscle memory.
    - Deterministic: the same `--seed` produces the same sample, the same pair selection, and the same
      histogram on the same database.
    - Unit tests run entirely against a Plan 13-03 fixture corpus in a temp file. No test reads
      `~/.memory/aaron.db`, and no test requires a network or an ONNX model.
  </behavior>
