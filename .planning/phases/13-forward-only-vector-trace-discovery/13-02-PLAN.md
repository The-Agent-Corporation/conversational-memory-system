<objective>
GAP-12-D. `decaySummary` (`sleep-reviewer.ts:304-334`) computes
`strength × 0.5^(ageHours / halfLifeHours)` where `ageHours` is measured from
`lastAccessedAt ?? retrievedAt ?? createdAt` — a field decay itself never advances. N runs therefore apply
`0.5^(N·age/halfLife)` and compound instead of converging. Measured on one clone: 5,138 hot summaries after
one pass, **1,679 after two** (`12-CLOSING.md:70-80`).

**The fix, chosen against R8's stated constraint.** `13-RESEARCH.md:439` names the natural fix — a
"decayed through" timestamp — and names its cost: `SummarySchema` has no such field and no `updatedAt`
(ADR 0052 §7), so adding one ripples into both stores, sync effect fingerprints, and every summary fixture.
The research offers the alternative and this plan takes it: **make decay a pure function of
`(referenceAt, now)` recomputed from an unchanging baseline, not applied to the previous result.**

Concretely:

    decayed = min(summary.strength, DECAY_BASELINE_STRENGTH × 0.5^(hoursBetween(referenceAt, reviewedAt) / halfLifeHours))

The `min` is load-bearing and is the whole reason no schema field is needed:

- **Idempotent.** Run 1 at time t yields `s1 = min(s0, d(t))`, so `s1 ≤ d(t)`. Run 2 at the same t yields
  `min(s1, d(t)) = s1`. Unchanged, so `decaySummary` returns null and no write occurs. That is R8(a).
- **Correct per half-life of ELAPSED TIME.** At `t + H`, `d(t+H) = d(t)/2`, so the value halves once per
  half-life of clock advance regardless of how many times the pass ran in between. That is R8(b).
- **Monotone.** It can never raise a strength, so a summary created weak stays weak. Without the `min`, a
  bare derived value would *raise* the strength of a recently-accessed weak summary — a silent behaviour
  change nobody asked for.

**Zero schema change. Zero store change. Zero sync change.** `Summary.strength` keeps its type and meaning;
what changes is that it is now a bound rather than an accumulator.

Second, smaller fix, required by `13-CONTEXT.md:147-149`: `decaySummaries` currently issues an **unfiltered
`listSummaries()`** (`:207`) and then filters in JS via `isDecayEligible`. On the live corpus that is
145,765 rows loaded and Zod-parsed to act on a subset. CONTEXT's note is explicit — `NON_SUPERSEDED_STATES`
includes `stale`, so decay cannot shrink a candidate set and **whatever bounds a pass must be an explicit
predicate, not a side effect of decay**. This plan makes the predicate explicit and pushes it into the
query. The JS predicate stays as a second line, exactly as `loadCandidates` re-applies its state filter
(`sleep-reviewer.ts:115-119`).

Purpose: GAP-12-D. Unblocks any later use of recency to bound a pass (SC5's natural route).
Output: idempotent decay, a bounded decay query, and R8's two assertions.
</objective>

    - **R8(a) — idempotence.** Seed a store with summaries of assorted `strength`, `halfLifeHours`,
      `lastAccessedAt`, and states. Call `decaySummaries({ reviewedAt: T })`. Call it again with the SAME `T`.
      Assert the second call returns `updatedSummaries: []`, and additionally assert `saveSummary` was not
      invoked on the second call (use a counting write store or a spy) — "returned empty" and "wrote nothing"
      are different claims and the bug could satisfy one without the other.
    - **R8(b) — halves once per half-life of elapsed time.** A summary with `strength: 1`,
      `halfLifeHours: 24`, `lastAccessedAt: T0`. Call decay at `T0+24h`, then `T0+48h`, then `T0+72h`.
      Assert strengths `0.5`, `0.25`, `0.125→0.13` (whatever `roundStrength` yields — compute the expectation
      from the formula in the test, do not hardcode a number the implementation could drift from).
      Then, from a fresh fixture, call decay **ten times** at `T0+24h` and assert the result is still `0.5`.
      That second half is the regression test: it is the exact shape that produced 5,138 → 1,679.
    - **Monotonicity.** A summary with `strength: 0.10`, `halfLifeHours: 24`, `lastAccessedAt` = `reviewedAt`
      minus one minute. The derived value is ~1.0, far above 0.10. Assert the summary is returned unchanged
      (i.e. `decaySummary` returns null) and its strength is still `0.10`. Decay must never raise a strength.
    - `:298`'s rule survives: `ageHours <= 0` still returns null before any arithmetic.
    - `:271`'s rule survives: `lastAccessedAt` is still preferred over `retrievedAt` over `createdAt`.
    - A summary whose derived strength falls below `staleStrengthThreshold` still transitions to `stale`.
  </behavior>
  <action>
    In `decaySummary`, replace the accumulating expression with the monotone derived form:

      const referenceAt = summary.lastAccessedAt ?? summary.retrievedAt ?? summary.createdAt;   // UNCHANGED
      const ageHours = hoursBetween(referenceAt, reviewedAt);
      if (ageHours <= 0) return null;                                                            // UNCHANGED
      const derived = DECAY_BASELINE_STRENGTH * Math.pow(0.5, ageHours / summary.halfLifeHours);
      const decayedStrength = roundStrength(Math.min(summary.strength, derived));

    Export `export const DECAY_BASELINE_STRENGTH = 1;` with a docstring that carries the whole argument:
    strength is a BOUND derived from recency, not an accumulator; the `Math.min` is what makes repeated
    invocation a no-op without a `decayedThroughAt` field; `SummarySchema` has no `updatedAt` and
    `contraction-runner.ts` sets `version: 1` unconditionally (ADR 0052 §7), so no monotonic write marker
    exists to carry one; and the observed symptom this closes is 5,138 → 1,679 (`12-CLOSING.md:70-80`).

    Everything else in `decaySummary` is unchanged: the reference-field selection, the `ageHours <= 0`
    guard, `roundStrength`'s clamp and 2-decimal rounding, the `staleStrengthThreshold` comparison, and the
    null return when neither strength nor state changed.

    **If one of the three pinned tests at `:246`/`:271`/`:298` changes its expected numbers**, do not adjust
    it silently. Change it, and add a comment on the changed expectation naming GAP-12-D and stating what
    the old number was and why the new one is correct. A reviewer must be able to tell an intended
    correction from a test bent to fit. If none of the three change, say so explicitly in the summary —
    that is a stronger result and should be reported as one.

    **State the semantic change, because it is larger than idempotence and the plans must not leave it in a
    docstring only (W8).** `strength` stops being an accumulator and becomes a recency-derived *bound*.
    Consequences a later reader will otherwise misattribute: a mid-strength summary now decays *less* per
    pass and reaches `stale` later than it does today, so the `stale` population after a pass changes shape;
    and `strengthen()` (`memory-retriever.ts:407-408`) still raises strength on retrieval and is unaffected,
    because raising is not decay. Record both in this plan's summary and in ADR 0055's "not addressed here"
    section (Plan 13-12), so a changed `stale` count is not later attributed to something else.

    Do NOT add a field to `SummarySchema`. Do NOT add a store method. Do NOT wire `decaySummaries` into any
    scheduler — it has no scheduler wiring today and giving it one is out of this phase's scope.
