## Part 1 — the resident index

`SummaryVectorIndex` is built from `SummaryVectorScanPage`s (Plan 13-05) and holds a contiguous
`Float32Array`, a parallel id array, and an id→row map. Two reductions `13-CONTEXT.md:68-72` names are
implemented here and, per that same paragraph, **measured rather than projected** — ADR 0054's 1.9×
optimistic sample on this exact corpus is the standing precedent:

- **Pre-normalise once.** Each row is scaled to unit length at insert, so cosine similarity becomes a dot
  product. Claimed ~2×; Plan 13-09 measures it.
- **Pair symmetry.** The all-pairs scan visits only `j > i`. Claimed ~2×; also measured.

Neither is required for the job to fit an overnight window (`13-CONTEXT.md:66-67`), so if measurement
contradicts the projection the correct response is to record the number, not to chase it.

## Part 2 — trace identity, decided

`13-RESEARCH.md:352-360` gives five candidate designs and the failure mode of each. The decision:

**Design 5 (recorded, not recomputed) is the mint/match POLICY. Design 4 (seed + recorded ordinal) is the id
DERIVATION. They are complements, not alternatives — `13-RESEARCH.md:360` says so directly, and answering
only "what id do I mint" is exactly what the current code does.**

- **Match before minting (S3).** Build reverse indexes `summaryId → traceId` from `listTraces()` and
  `summaryId → proposalId` from `listProposals({ state: "proposed" })`, plus a rejected-grouping index from
  `listProposals({ state: "rejected" })`. Ask "does a live trace already cover both of these summaries?"
  by **membership overlap**, never by id — id-matching is precisely the unstable thing
  (`trace-proposal-planner.ts:94-103`). Cost is O(existing traces + proposals), never O(corpus), so it
  composes with SC5.
- **Mint id (S1/S2).** `trace_v1_<sha256(personId, seedSummaryId, ordinal)>[0:16]`, where `seedSummaryId`
  is the member minimising `(createdAt, id)` **at mint time** and `ordinal` is the number of already-live
  traces sharing that seed, assigned at mint. Both are **recorded in the payload**, never recomputed.
- **Fail closed on seed drift.** If a late-imported summary would later make a different member the
  earliest, the **recorded id wins — do not re-mint.** Design 3's named failure mode is exactly this, and
  this repo demonstrably has late-insert paths (the drift guard at `contraction-runner.ts:192-203` exists
  for them).

Designs explicitly rejected, recorded so nobody reaches for them later:

| Design | Why not |
|---|---|
| 1 — member-set hash | **The current bug in a new costume.** Adding one summary changes the set, changes the id, mints a new trace, orphans the old. It is the "obvious deterministic" answer and it is wrong. |
| 2 — min member id | Summary ids are sha256 hex (`contraction-runner.ts:872-875`), so a new member becomes the new lexicographic minimum of a k-member trace with probability ≈ 1/(k+1) — routine for 2- and 3-member traces, not rare. |
| 3 — bare time-ordered seed | Right under strictly forward-only growth, but a hub summary near many neighbours seeds several distinct traces, so a bare seed collides (S2 fails). Fixed by design 4's ordinal. |

Note the payoff at the accept path: `approveTraceProposal` (`proposal-reviewer.ts:226-262`) is **already an
upsert by `payload.traceId`** that preserves `existing?.createdAt` and returns an empty `createdTraceIds`
when the trace already existed. A stable id therefore makes re-acceptance an *update*, not a new trace,
with zero change to the accept path. SC3 costs nothing here.

**One member-set hash IS used, and only here:** the rejected-grouping key. `13-RESEARCH.md:362-367` finds
that a rejected *trace* suppresses re-proposal but a rejected *proposal* does not, so a user rejects a
proposal and the next cycle proposes it again, forever — and on a capped design that deliberately re-offers
suppressed candidates, that becomes the dominant source of review-queue churn. Rejection memory wants
"this exact grouping was rejected", which is a set question, so a set hash is the right tool for it and the
wrong tool for identity. Both facts live in this module, adjacent, with the distinction spelled out.

| Boundary | Description |
|----------|-------------|
| identity rule → trace assignment stability | an unstable id orphans traces and re-mints on every run (SC4) |
| id collision → silent merge | `approveTraceProposal` upserts by `payload.traceId`, so a collision merges two unrelated traces |
| pure module → I/O | a store reference here would reopen the 154-hour shape |
