<objective>
Locked decision 1 (`13-CONTEXT.md:79-100`): the existing 56,706 summaries are bootstrapped against each
other in a single bounded, resumable, idempotent, offline pass — because pure forward-only satisfies the
ROADMAP goal literally while producing nothing useful for months, every summary that exists today remaining
permanently traceless.

## The bootstrap emits no proposals — and that is what makes it idempotent

`13-RESEARCH.md` Open Question 5 asks whether the bootstrap emits proposals or proposed traces.
**Decision D-13-4: neither. The bootstrap emits a ranked backlog into the Phase-13 checkpoint, and the
daemon drains it at `emissionCap` per cycle through the unchanged `commitProposalRun` path.**

Four consequences, each of which removes a whole class of risk:

1. **Idempotence is structural.** "Running it twice must not produce duplicate traces or duplicate
   proposals" (`13-CONTEXT.md:96`) holds because it produces zero of either. R2's third assertion — a
   completed bootstrap re-run emits zero new proposals — becomes true by construction rather than by a
   dedupe check that could be wrong.
2. **`commitProposalRun`'s preconditions dissolve.** It needs a `jobId`, an `expectedJob`, and an exact-record
   CAS on the contraction checkpoint (`sqlite-store.ts:822-861`), plus an authority whose operation the store
   accepts (`13-RESEARCH.md` Open Question 4). An offline job has none of those. Not publishing means not
   inventing a second publication path or a new `WriteAuthority` kind with sync implications.
3. **One publication path.** SC3's strongest form: every trace proposal that has ever existed came out of
   `commitProposalRun`, whether its candidate was found by the bootstrap or by a forward cycle.
4. **Emission stays capped and reviewable.** 56,706 summaries would otherwise produce a proposal volume that
   poisons `DerivationInvalidator`'s unfiltered `listProposals()`/`listTraces()` inside every rewind
   contraction slice (R9, `derivation-invalidator.ts:92,100`). The backlog is one bounded checkpoint row.

**The cost of the choice, stated honestly.** The backlog is capped at `backlogCap` (default 1,000), so the
lowest-scoring candidates of a full scan are dropped. They are **recomputable, not lost**: this command is
deterministic, so re-running it after the backlog drains reproduces the next tier exactly. The result
reports `backlogDropped` so the truncation is visible, per ADR 0054's "no silent caps". This is the
reasoning D-13-2 (Plan 13-06) records and it is restated here because this is where the drop actually happens.

## Making the 154-hour shape impossible, and provable

`13-CONTEXT.md:52`: a bootstrap calling `findNearestSummaries` per summary costs 56,706 × 9.8 s ≈ 154 hours.
Three independent defences:

- **Structural.** The scan runs on `SummaryVectorIndex`, which holds no store reference and cannot query.
- **Counted.** `assertFlatCost` over two corpus sizes, on calls **and** rows, with `findNearestSummaries`
  asserted at exactly 0. Per `13-RESEARCH.md:386`, equality across two sizes — a ceiling passes for an O(n)
  implementation at n=5.
- **Measured.** Plan 13-09's full-scan number sizes the batch and yield budget, replacing the 69.9-minute
  projection with what the corpus actually did.

## Resumability, following the contraction-runner precedent

The resume key is a **position in a fixed enumeration** — the index of the last completed left row of
`scanPairs`, held as a `summaryId` in the index's stable ascending order. That is exactly the distinction
`13-RESEARCH.md:241` draws: an id watermark is a valid enumeration position (right for the bootstrap) and is
not a "since last pass" watermark (wrong for the forward cursor, which Plan 13-06 gives its own field).

**Do not extend the contraction checkpoint** — the three verified reasons are in Plan 13-06's objective, and
reason 2 is the sharp one: a bootstrap writing into that record out-of-band makes the daemon's next
`commitProposalRun` throw `"Proposal run state changed"`.

## The handoff is part of the job, not the next job's problem (B2)

An earlier draft had the final batch set `bootstrapComplete: true` and `bootstrapAfterSummaryId`, and
**nothing at all** set `cursor`. That leaves the forward cursor null, and a null cursor starts
`listSummaryVectorIdsCreatedAfter` at the beginning of the `(created_at, summary_id)` enumeration. On the
live corpus every one of the 56,706 vector rows was written by the Phase 10/12 backfill and sorts *before*
any new summary — so the daemon would have evaluated summaries #1-32 of history per cycle for roughly
1,772 cycles, about 74 days at a 60-minute forced interval, reporting a healthy cycle every hour while
doing nothing useful. A success-shaped zero, which is the exact defect commit `4c7773c` was written to fix.

**Decision D-13-7: bootstrap completion sets the forward cursor, atomically with `bootstrapComplete`.** The
value is `getLatestSummaryVectorCursor(personId, provider, model)` (Plan 13-06) — one indexed query,
returning the maximum `(createdAt, summaryId)`, whose round trip to an empty
`listSummaryVectorIdsCreatedAfter` is asserted on both stores. Reading it at completion time rather than at
start time is deliberate: a vector written *during* a multi-hour bootstrap is genuinely new work the
forward path should skip only if the bootstrap actually covered it, and the bootstrap's enumeration is by
`summaryId`, not by time. Take the maximum at completion and record in the summary that a vector written
mid-run is covered by the scan if its id sorted after the resume position and by the forward path
otherwise — never by neither.

Plan 13-10 carries a fail-closed second line that refuses to run when the cursor is null on a non-empty
corpus, so a regression here is a loud skip rather than 74 silent days.
