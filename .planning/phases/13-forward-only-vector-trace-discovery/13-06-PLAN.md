<objective>
The durable state forward-only discovery needs, and the resolution of the phase's sharpest open design
question.

## Where the checkpoint goes — and where it must not

`13-RESEARCH.md:229-233` gives three verified reasons **not** to extend `ContractionCheckpointSchema`, and
this plan honours all three:

1. `saveContractionCheckpoint` asserts the referenced contraction **job exists and is person-owned**
   (`sqlite-store.ts:480-481`). The offline bootstrap has no contraction job.
2. `commitProposalRun` performs an exact-record CAS on that checkpoint
   (`sqlite-store.ts:832-838`, `sameRecord(currentCheckpoint, parsed.expectedCheckpoint)`). A Phase-13
   field written out-of-band would make the daemon's next `commitProposalRun` throw
   `"Proposal run state changed"` — a real collision, silent until it is not.
3. `ContractionCheckpointSchema` is `.strict()` and rows are round-tripped through
   `getPayload(..., ContractionCheckpointSchema)`. A new required field makes every pre-existing row fail
   to parse.

So Phase 13 gets its own table and its own schema. Migration 6 is additive
(`create table if not exists`), append-only, and mutates no earlier entry.

## Resolving R5 — the cap-versus-cursor tension

`13-RESEARCH.md:420-423` calls this *the most important unresolved design question in the phase* and says
to settle it before the vector waves rather than discover it inside them. `13-CONTEXT.md:122-123` binds the
answer: the cap bounds *emission*, not correctness, and **the next cycle must be able to reach what this
one suppressed rather than losing it permanently.**

The research offers two resolutions: (a) the cursor advances only over fully-emitted work, or (b)
suppressed candidates are persisted as a backlog.

**Decision D-13-2: (b), and (a) is explicitly rejected.**

(a) is rejected because it creates head-of-line blocking. One hub summary with several thousand
above-threshold neighbours would pin the cursor at that summary for hundreds of cycles, and every genuinely
new summary arriving behind it would go unevaluated for months. That failure is worse than the one (a)
prevents, and it is silent — the receipt would say "cycle ran, 20 proposals" every night while the corpus
frontier stood still.

(b) as specified here:

- The forward cursor `{ createdAt, summaryId }` advances on **every** successful cycle, over every summary
  the cycle evaluated, regardless of how many of that summary's candidates were emitted.
- Candidates the cap suppressed are written into the checkpoint's `backlog`, ordered by score descending
  with a `summaryIds`-lexicographic tiebreak, capped at `backlogCap`.
- The next cycle emits from `merge(backlog, freshCandidates)` under the same ordering, so a backlog entry
  competes with new work on score and cannot be starved by arrival order.
- Overflow past `backlogCap` is **dropped and reported**, never silently discarded (ADR 0054's "no silent
  caps", `13-CONTEXT.md:119-121`). The dropped entries are the lowest-scoring, and they are **recomputable**
  rather than lost: the bootstrap (Plan 13-11) is idempotent and deterministic, so re-running it after the
  backlog drains reproduces the next tier exactly. That recomputability is what makes a bounded backlog
  compatible with "not losing it permanently"; state it in the receipt's documentation so the property is
  not accidentally removed later.

`backlogCap` default: **1,000.** At the per-cycle emission cap of 20 that is fifty cycles of review queue —
far more than can be reviewed in the window it takes to refill — while keeping the checkpoint payload around
150 KB, which is a flat per-cycle read/write cost independent of corpus size.

## The forward cursor's substrate

Summary ids are content-addressed hashes, not time-ordered (`contraction-runner.ts:872-875`), so an id
watermark is a valid position in a fixed enumeration (fine for the bootstrap's resume) but is **not** a
"since last pass" watermark (`13-RESEARCH.md:241`). `Summary.createdAt` lives inside payload JSON with no
index. `summary_vectors.created_at` is a real column, and Phase 12's post-commit embed stage keeps it
current for exactly the summaries the daemon produced — so it is the right substrate. Migration 6 adds
`idx_summary_vectors_person_created (person_id, created_at, summary_id)` to make the range scan
index-ordered, and Task 3 guards it with the ADR 0054 triple.

## Guards before the thing they guard (B4)

Migration 6 adds a `person_id`-leading index to `summary_vectors` — the table both `findNearestSummaries`
(`sqlite-store.ts:1814-1820`) and `listSummaryVectorScanPage` read on **every** call. That is the same shape
as ADR 0054's 388× incident, which returned correct results, broke two optimizations, and failed no
assertion. Plan 13-04 established the discipline for a *smaller* change: write the plan assertions first, so
the first run is a measurement rather than a confirmation. This plan follows it — **Task 2 captures the
three "still uses" baselines before Task 3 appends the migration.** An earlier draft inverted that order;
it is corrected here.

Fixture-scale plans are **necessary and not sufficient.** SQLite's index choice is row-count dependent, and
13-04 Task 3 says so in its own words: *"A plan that is index-covered on 500 rows and not on 145,765 is
exactly the failure mode this step exists to find."* Plan 13-12 Part B therefore re-runs all five
assertions against a migration-6 clone at real row counts, with the same STOP-on-failure rule. Neither
check replaces the other.

## The bootstrap→forward handoff needs a watermark, cheaply (B2)

The cursor is `null` before the first successful cycle, and a null cursor starts
`listSummaryVectorIdsCreatedAfter` at the beginning of the enumeration. On the live corpus every one of the
56,706 vector rows was written by the Phase 10/12 backfill and sorts *before* any new summary — so a
bootstrapped-but-null cursor would make the first forward cycles re-walk history at `evaluationBudget`
rows an hour, roughly 74 days of healthy-looking receipts doing nothing useful. That is the failure shape
commit `4c7773c` and ADR 0054 both exist because of.

Closing it needs one cheap primitive, added here: `getLatestSummaryVectorCursor`, a single indexed
`order by created_at desc, summary_id desc limit 1`. Plan 13-11 calls it to set the cursor atomically with
`bootstrapComplete`, and Plan 13-10 uses it to detect the null-cursor-on-non-empty-corpus state and refuse
loudly rather than walk history.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Phase-13 checkpoint → contraction checkpoint CAS | an out-of-band write into the contraction record breaks `commitProposalRun` |
| cursor enumeration → retrieval boundary | the cursor is a position enumerator and is NOT a filtered read; its consumer enforces the boundary |
| migration 6 index → existing query plans | ADR 0054: a steal is invisible to every output assertion |
| checkpoint payload → per-cycle cost | an unbounded backlog would make the checkpoint grow without limit |
