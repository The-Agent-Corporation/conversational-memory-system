<objective>
Forward-only discovery inside a daemon cycle. This plan is where SC2, SC4, and SC5 are earned.

## Publication — decided, and it is the conservative choice

`13-RESEARCH.md` Open Question 5 asks whether discovery emits proposals or proposed traces directly.
**Decision D-13-3: proposals only, published through the existing path, unchanged.**

`TraceDiscoveryRunner` is invoked *by* `ProposalScheduler.runDue`, and its proposals are merged into
`staged.proposals` before `validateStagedReview`. Nothing about `validateStagedReview` (`:133-155`),
`commitProposalRun` (`sqlite-store.ts:822-861`), or `approveTraceProposal` (`proposal-reviewer.ts:226-262`)
changes. That is the strongest possible form of SC3, and it dissolves Open Question 4 for the daemon path —
the authority is the one `ProposalScheduler` already captured.

Discovery is **not** driven through `SleepReviewer.loadCandidates`. The reviewer keeps
`NullTraceProposalPlanner` from Plan 13-01 permanently; that injection stops being a holding action and
becomes the design. The scheduler owns trace discovery directly, with its own bounded reads.

**Be honest about what SC2 does and does not remove.** `loadCandidates` still runs, because `proposeBoxes`
still needs it (`sleep-reviewer.ts:146-158`). SC2 says "to find new **traces**", which is satisfied — but
the box path remains the dominant cost of a review cycle. `13-RESEARCH.md:199` says to state this rather
than imply the load is gone, and this plan states it in the summary, in the runner's docstring, and in
ADR 0055.

## SC4 — two halves, and only one of them was ever "by construction"

SC4: *running the trace-discovery step twice with exactly one new summary added between runs leaves every
pre-existing trace assignment unchanged.*

**The trace half holds by construction.** Discovery never mutates a trace — it emits proposals, and
assignments change only when a human accepts one. So `listTraces()` is byte-identical across a discovery
run, always.

**The proposal half does not hold by construction, and an earlier draft of this plan wrongly claimed it
did.** `commitProposalRun` upserts proposals by id (`sqlite-store.ts:838-842`), so any scheme that reuses
one id across two memberships overwrites rather than adds — in exactly SC4's literal scenario. It holds
now because of **D-13-6** (Plan 13-08): proposal ids are membership-derived
(`proposal_trace_${traceId}_${sha256(sorted memberIds)[0:8]}`), so a new candidate is a new id and
therefore an addition, while an identical re-proposal is a byte-identical upsert; and a candidate
overlapping a live *proposed* proposal is suppressed until that proposal is decided, so the queue does not
fill with variants. ADR 0055 records the correction alongside the claim.

Combined with Plan 13-07's mint-once identity, nothing churns and nothing collapses into a mega-trace.

## B2 — a bootstrapped corpus must never be walked from the beginning

`TraceDiscoveryCheckpointSchema.cursor` is nullable, and a null cursor starts
`listSummaryVectorIdsCreatedAfter` at the beginning of the `(created_at, summary_id)` enumeration. On the
live corpus all 56,706 vector rows were written by the Phase 10/12 backfill and sort *before* any new
summary, so a bootstrapped-but-null cursor makes the first forward cycles evaluate summaries #1-32 of
history — roughly 1,772 cycles, ~74 days at a 60-minute forced interval, every receipt reporting a healthy
cycle while nothing useful happens. That is the shape commit `4c7773c` exists because of: a
success-shaped zero.

Plan 13-11 sets the cursor at bootstrap completion. **This plan does not trust it to.** The runner treats
"cursor is null AND the corpus is non-empty" as a distinct, reported, refused state rather than as a
starting position — a fail-closed second line, so a regression in 13-11 produces a loud skip instead of 74
silent days.

## The corpus is loaded once per process, never per cycle

Per D-13-1 (Plan 13-03) a per-cycle O(corpus) read violates SC2 even at one call, and per D-13-1a a
once-per-process warm-up does not, because SC2's subject is "a daemon trace-discovery **cycle**". The runner
therefore:

- builds `SummaryVectorIndex` once, by paging `listSummaryVectorScanPage`, on first use;
- **appends** to it thereafter, from the same page read that fetches the cycle's new vectors — the daemon
  holds the write lease and is the single writer, so the index cannot go stale behind its own back;
- proves it with `assertOncePerProcess`: N cycles at both corpus sizes, and the page-read call count is 1.

**`memory daemon once` collapses the exemption, and that must be named rather than discovered (W3).**
`runOnce` (`daemon.ts:246-332`) has its own loop and one invocation is one process, so every
`memory daemon once` pays a full corpus warm-up before its single cycle. Plan 13-12 Part B step 9 measures
a cycle with exactly that command, so its number is warm-up **plus** cycle unless the two are reported
separately — which that step now requires. The runner's docstring and ADR 0055's D-13-1b both state it, so
a `daemon once` timing is never read as steady-state cost.

And the honest limit, recorded rather than papered over (D-13-1b): the dot-product term is O(N) per queried
summary and cannot be made sublinear without an ANN index, which `13-CONTEXT.md:169-172` puts out of scope.
It is bounded instead by a configured cap on summaries evaluated per cycle, and by the measured 74 ms/scan
from Plan 13-09. ADR 0055 records this as a stated limitation, not as flatness the design does not have.

      strictly after S, obtained via `listSummaryVectorIdsCreatedAfter` with `limit: evaluationBudget`. It

    - **Cursor advances unconditionally** (D-13-2): after a successful cycle the checkpoint's cursor is the

    - **Backlog round trip.** Cycle 1 with 3× the cap emits `cap` and writes the remainder to the
      checkpoint's backlog. Cycle 2 with **zero** new vectors emits `cap` more, drawn from the backlog, and
      shrinks the backlog by exactly that many. Cycle 3 the same, until the backlog empties. This is R5,
      end to end through the durable checkpoint rather than in the planner alone.
    - **Bounded evaluation.** `evaluationBudget` (default 32) caps summaries evaluated per cycle. The budget
      goes INTO the cursor query as `limit`, never an unbounded query sliced in JS — the
      `embedding-repair.ts:105-112` rule.
    - **B2 fail-closed guard.** With a corpus that has vectors, `bootstrapComplete: true`, and
      `cursor: null`, `run()` returns `skipped: "cursor-uninitialised"` carrying the corpus size and
      `getLatestSummaryVectorCursor`'s value, does **no** evaluation, and does not throw. Same for a corpus
      with vectors and no checkpoint at all: `skipped: "bootstrap-required"`. Assert that in neither case
      does `listSummaryVectorIdsCreatedAfter` get called with a null watermark. An empty corpus (no vectors)
      is not an error — it returns a clean zero-work result.
    - **B2 happy path.** With `bootstrapComplete: true` and a cursor equal to
      `getLatestSummaryVectorCursor(...)`, adding exactly one new vector and running one cycle evaluates
      **exactly one** summary. Assert the count, not merely that it is small.
    - **Residency guard.** With `maxIndexBytes` set below the fixture's `approximateBytes()`, `run()` returns
      a result flagged `skipped: "index-budget-exceeded"` with the two byte figures, does no work, and does
      NOT throw. A daemon that OOM'd twice at a 4 GB heap must refuse loudly rather than allocate hopefully.
    - **Never throws.** Like `EmbeddingRepairRunner.runDue`, `run()` returns a result on every path — a store
      error, a corrupt checkpoint, an empty corpus, a zero-dimension index. A test injects a throwing store
      method for each and asserts a result with a populated `failure` field comes back.
    - **Rate limited** by an injected monotonic clock, `minimumIntervalMs`, set before the work so a
      persistently failing pass is still rate limited (`embedding-repair.ts:100-103`).
    - **Corrupt checkpoint is fail-safe:** a checkpoint whose `version` is unrecognised or which fails Zod
      is treated as absent, the cycle re-warms from the beginning of the enumeration, and the event is
      reported in the result. It must never throw and must never silently drop the backlog without saying so.
