<objective>
Option A from `13-RESEARCH.md:264-273`, in the shape that makes Option B possible: **one paged, packed,
boundary-enforcing bulk vector read**.

This is the mechanism that makes the 154-hour shape structurally impossible. `13-CONTEXT.md:52` measures it:
a bootstrap that called `findNearestSummaries` once per summary costs 56,706 × 9.8 s ≈ 154 hours. The
guarantee this plan supplies is stronger than a budget — the consumer built on top of it (Plan 13-07's
`SummaryVectorIndex`) holds **no store reference at all**, so it physically cannot issue a query per
summary. Structure first, then the count test that pins it.

Three shape decisions, each with its reason:

1. **Paged, not whole-corpus.** `{ afterSummaryId, limit }` over a stable ascending `summary_id` order.
   The bootstrap needs to yield cooperatively inside the 30 s lease TTL (`cooperative-yield.ts`), and the
   caller — not the store — must own the memory ceiling. A single unbounded call would put an 87 MB-plus
   allocation decision inside the storage layer where no caller can bound it.
2. **Packed, not boxed.** `SummaryVectorRecord.vector` is `number[]` (`memory-store.ts:90`), and 56,706 ×
   384 boxed JS numbers is far more than the 87 MB `13-CONTEXT.md:64` quotes — that figure is for
   `Float32Array` storage. `13-RESEARCH.md:272` names this explicitly as Option A's second cost and says to
   measure rather than assume. The page therefore returns one contiguous `Float32Array` of length
   `rowCount × dimensions` plus a parallel `summaryIds: string[]`. `unpackFloat32Vector`
   (`embeddings/vector-codec.ts`) already exists; this writes into a preallocated buffer instead of
   allocating per row.
3. **The boundary lives here, not above.** `13-RESEARCH.md:273` is emphatic: the GAP-11-A fail-closed
   retrievable sweep lives *inside* `findNearestSummaries`, and a bulk method that omits it re-opens
   GAP-11-A **in a new place** — which is the exact failure ADR 0054 §3 names ("GAP-11-G was caused by
   re-implementing a hygiene walk in a second place"). So `listSummaryVectorScanPage` enforces
   `personId` + `allowedScopeIds` + `RETRIEVABLE_MEMORY_STATES` using the **same bound predicate Plan 13-04
   just established**, and R6's parity fixture proves both stores agree.

**Option C was rejected** and this plan does not touch `findNearestSummaries`' signature.
`13-RESEARCH.md:288-296`: batching N queries amortises the two loads by N, which fixes the bootstrap and
does nothing for the daemon, where N is a handful and per-cycle cost stays O(corpus) — the thing SC2
forbids. It also widens a security-sensitive method that four boundary tests pin and that Phase 14 is about
to become the primary consumer of, coupling two phases.

Purpose: REQ-046, REQ-047; SC2.
Output: one new `MemoryStore` method, both implementations, and the R6 parity block.
</objective>

    Add to `memory-store.ts`:

      export interface SummaryVectorScanQuery {
        provider: string;
        model: string;
        personId: string;
        allowedScopeIds: string[];
        /** Exclusive lower bound in ascending summary_id order. Null/undefined starts at the beginning. */
        afterSummaryId?: string | null;
        /** Maximum rows in the returned page. Required — the caller owns the memory ceiling. */
        limit: number;
      }

      export interface SummaryVectorScanPage {
        dimensions: number;
        /** Ascending by summaryId. Length is the page's row count. */
        summaryIds: string[];
        /** Contiguous, length === summaryIds.length * dimensions. Row i occupies [i*dimensions, (i+1)*dimensions). */
        vectors: Float32Array;
        /** Pass as the next call's `afterSummaryId`. Null when this page is the last. */
        nextAfterSummaryId: string | null;
      }

      listSummaryVectorScanPage(query: SummaryVectorScanQuery): Promise<SummaryVectorScanPage>;

    Write the docstring to carry the whole contract, in the style of `listSummaryIdsMissingVector`'s:

    - **What it returns:** every `summary_vectors` row for `(provider, model, personId)` whose summary is in
      a `RETRIEVABLE_MEMORY_STATES` state and whose effective scope ids (empty ⇒ `["personal"]`) are all
      within `allowedScopeIds`, and whose `dimensions` match the page's `dimensions`. Identical boundary to
      `findNearestSummaries`, from the same predicate source. A row failing any of these is absent, not
      zeroed.
    - **`dimensions`:** taken from the first in-boundary row; rows with a different `dimensions` are
      excluded, mirroring `findNearestSummaries`' `row.dimensions !== query.vector.length` skip. An empty
      page reports `dimensions: 0`.
    - **Ordering and paging:** strictly ascending `summaryId`, so `afterSummaryId` is a stable resume key
      across processes and across both stores. A page is a pure prefix of the remainder — calling with a
      smaller `limit` returns the same rows in the same order.
    - **Why it exists and what it must never become:** it is the once-per-job corpus load that makes
      per-summary `findNearestSummaries` calls unnecessary. `13-CONTEXT.md:52` — a per-summary loop is
      56,706 × 9.8 s ≈ 154 hours. State plainly that this method must never be called once per summary, and
      that Plans 13-10/13-11 pin that with `assertFlatCost`.
    - **What it deliberately does NOT return:** summary payloads, summary text, or `Summary` objects. A
      caller needing those resolves the small candidate set with `listSummariesByIds`. Loading payloads here
      would reintroduce the 7.04 s / 1,296 MB cost Plan 13-04 just removed.
  </action>
