# GAP-12-A — The embedder's advertised model and its emitted model differ, so the backfill never converges

**Status:** open — blocks the Phase 12 backfill and any missing-set-driven daemon repair pass
**Found:** 2026-07-28 by the Phase 12 researcher, reproduced by running the real code
**Verified independently by the orchestrator** in source, 2026-07-28

## What it is

`TransformerEmbedder` advertises one model identity and stamps another:

| location | value |
|---|---|
| `src/embeddings/transformer-embedder.ts:32` | `readonly model = "Xenova/bge-small-en-v1.5"` |
| `src/embeddings/transformer-embedder.ts:103` | emits `model: \`${this.model}@${this.revision}\`` |

`backfill-embeddings-command.ts` uses **both**, for two different purposes:

- line 64 — queries the missing set with `listSummaryIdsMissingVector(embedder.provider, embedder.model)`
  → the bare identity, no `@revision`
- line 102 — writes rows with `model: embedding.model` → the `@revision` identity

The query key and the write key are different strings, so a row written by the backfill never satisfies
the `not exists` predicate that produced it. **The missing set never shrinks.**

Measured by the researcher: after a complete run over 3 summaries, `listSummaryIdsMissingVector` still
returns all 3, and a second full run re-embeds all 3.

## Consequences on the live corpus

- A kill-and-restart of a 20–56 minute backfill **resumes from zero** — Phase 10's SC2 (resume without
  re-embedding) is not actually satisfied for this embedder.
- Phase 10's SC3 (a second full run performs zero additional writes) is not satisfied either.
- `memory status` reports `missingVectors == totalSummaries` permanently.
- Any daemon repair pass driven by the missing set would **re-embed the entire corpus every tick** — the
  precise failure SC2 of Phase 12 forbids.

## Why Phase 10's tests did not catch it

`tests/operations/backfill-embeddings-command.test.ts:9-10` hardcodes
`PROVIDER = "deterministic"` / `MODEL = "keyword-hash-v1"`. `DeterministicEmbedder` is the **only**
embedder whose class `model` and emitted `model` are identical, so the two keys coincide and every
assertion passes. No backfill test exercises `TransformerEmbedder` at all.

This is worth recording as a testing lesson, not just a bug: the fixture chose the one input value that
makes a two-key mismatch invisible. A test matrix over BOTH embedders would have caught it on day one.

## Fix direction

One identity, used for both the query and the write. Decide deliberately whether the canonical identity
includes `@revision` — it probably should, since REQ-045 requires recording provider/model/**version** so
stale-model vectors are detectable, and a revision-less key cannot distinguish them. Whatever is chosen
must be applied consistently in the embedder, the resolver, the backfill query, and `memory status`.

Pin it with a regression test that runs the backfill against `TransformerEmbedder` (or a fake whose class
`model` differs from its emitted `model`), asserting the missing set actually shrinks to zero and a second
run writes nothing.
