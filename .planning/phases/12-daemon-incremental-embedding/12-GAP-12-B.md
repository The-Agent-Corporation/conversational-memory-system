# GAP-12-B — The missing-vector query has no state predicate, so backfill would embed 89,059 superseded rows

**Status:** open — cost and scope defect; changes what "backfill the corpus" means
**Found:** 2026-07-28 by the Phase 12 researcher
**Verified independently by the orchestrator** in source and against the live corpus, 2026-07-28

## What it is

`SqliteStore.listSummaryIdsMissingVector` (`src/storage/sqlite-store.ts:1692-1704`) selects
`from summaries` with a `not exists` guard on `summary_vectors` and **no state predicate**:

```sql
select id from summaries
where not exists (
  select 1 from summary_vectors sv
  where sv.summary_id = summaries.id and sv.provider = ? and sv.model = ?
)
order by id asc
```

Measured on the live corpus (read-only, 2026-07-28):

| state | rows |
|---|---:|
| `compacted` (retrievable) | 49,314 |
| `superseded` | 89,059 |
| **total the backfill would process** | **138,373** |

## Why it matters

`findNearestSummaries` (`sqlite-store.ts:1712-1725`) deliberately filters superseded rows out of vector
search, and `rebuild-derivations` tombstones their vectors. So the backfill would spend the majority of
its runtime embedding rows that vector search will never return.

At the researcher's measured 24.2 ms/summary:

| scope | time | vector bytes |
|---|---|---|
| 138,373 (as written) | **≈56 min** | ~2.8× |
| 49,314 (retrievable only) | **≈20 min** | baseline |

## This corrects `12-CONTEXT.md`

The context document recorded the backfill scope as "49,314 summaries". That is the **retrievable** count,
not what the current query returns. The orchestrator wrote that figure; it is wrong as a statement about
backfill cost and is corrected here rather than left to be discovered mid-run.

## It also reopens a closed owner decision

On 2026-07-28 the owner closed Plan 11-13's superseded-summary prune as **unneeded**, on the stated
grounds that superseded rows are already excluded from retrieval and the database file does not shrink
without a `VACUUM`. Both remain true.

What was **not** known at the time is that those rows would be **embedded**. That is a new, concrete cost
that did not exist when the decision was made: ~36 extra minutes of backfill and ~2.8× the vector storage,
for rows that vector search filters out.

The purpose-built `memory prune-superseded` command already exists
(`src/cli/command-registry.ts:45`) with a dry-run default and a fail-closed backup gate.

**This is an owner decision, not a planner decision.** Two coherent options:
1. Prune superseded rows before backfilling — smallest corpus, fastest run, least storage.
2. Add a state predicate to the missing-set query — leaves the rows in place but stops embedding them.

Option 2 is arguably the more correct product fix regardless of the prune, since a superseded row should
not be a backfill candidate on any corpus. The two are not mutually exclusive.
