# Stack Research: Vector-Native Traces + Semantic Recall

**Domain:** Local embedding generation + sub-linear-ish nearest-neighbor search for a deterministic, local-first Node/TypeScript/SQLite memory system
**Researched:** 2026-07-21
**Confidence:** MEDIUM-HIGH (versions verified live via `npm view`; determinism claims verified against ONNX/sqlite-vec docs and issue trackers; some CPU-microarchitecture claims are MEDIUM confidence, training-data + WebSearch corroborated)

## Context Recap (read from codebase, not re-researched)

- Storage uses Node's **built-in `node:sqlite`** (`DatabaseSync`), not `better-sqlite3` (`src/storage/sqlite-store.ts`, `src/types/node-sqlite.d.ts`). This materially changes ANN-extension integration advice vs. generic "use better-sqlite3" guidance found in most tutorials.
- `Embedder` interface + `DeterministicEmbedder` (64-dim keyword-hash, SHA-256-seeded, no floats beyond a final normalize) already exist at `src/embeddings/embedder.ts`. `cosineSimilarity` and brute-force scoring already exist in `src/retrieval/memory-retriever.ts`.
- `Summary.embedding` is a nullable field already wired through ranking (`embeddingScore()` falls back to keyword overlap when embedder/embedding is absent or model/provider/dimension mismatch) — the plumbing for swapping embedders is already in place; this milestone is about what fills `Embedder` and what indexes `Summary.embedding.vector`.
- REQ-040 (verbatim): "Deterministic/local operation and tests shall not require an external LLM. Model-backed summarization or planning shall remain optional and adapter-gated." PROJECT.md restates this as a product boundary: "External models are optional adapters, never a local correctness dependency."
- ADR 0047 (zero-knowledge sync) treats embeddings as a **locally recomputed derived cache**, never synced or hashed for integrity ("Recompute only affected summaries, topics, boxes, traces, and embeddings locally. Derived caches are never independent authority"). This is important: cross-device bit-identical embeddings are **not** a sync-correctness requirement, only a nice-to-have for consistent ranking.

## Determinism Analysis (the critical question)

**DeterministicEmbedder (existing):** Fully deterministic across machines. Uses `sha256(token)` for bucket index/sign, integer accumulation, single floating-point normalize at the end. IEEE 754 basic ops (`sqrt`, `/`) are themselves deterministic for a given input on any conformant runtime — there's no reduction-order ambiguity because there's no matrix multiply or SIMD-parallel summation happening across an unspecified number of lanes/threads. This is the only option in this stack that is provably bit-identical everywhere. It captures only keyword co-occurrence (bag-of-hashed-tokens), not semantics — synonyms, paraphrase, and word order are invisible to it.

**ONNX-based transformer embeddings (transformers.js, fastembed, node-llama-cpp GGUF):** All CPU-only ONNX/GGML inference is deterministic **on a single fixed machine with a fixed thread count and fixed execution provider** — same weights in, same floats out, every run, because there is no sampling/dropout at inference time and CPU execution (unlike GPU) does not race independent kernels non-deterministically. However, **bit-exact reproducibility across different machines/architectures is not guaranteed**: floating-point addition is not associative, and different CPUs (or the same CPU with a different `intraOpNumThreads` / SIMD width, e.g., AVX2 vs AVX-512 vs ARM NEON on Apple Silicon vs. an older Intel Mac) can sum the same numbers in a different order, producing embeddings that differ in the last few mantissa bits. This is a documented, widely-discussed property of ONNX Runtime and neural inference generally, not a bug — parallel/SIMD execution always risks reduction-order variance across configurations.

- **Why this is acceptable here:** ADR 0047 already treats embeddings as a per-device, locally-recomputed derived cache — never synced, never hashed for cross-device integrity. Tiny cross-machine float drift in an ONNX embedding therefore cannot break sync correctness; at worst it could cause a device to rank two nearly-tied candidates in a different order than another device, which is cosmetic, not a correctness violation of REQ-040 (REQ-040 is about not requiring an *external* model/service, not about bit-for-bit cross-device embedding equality).
- **Mitigation to make same-machine determinism airtight:** force `intraOpNumThreads: 1` (or a fixed, pinned value) and FP32 (not FP16/BF16, which the literature flags as visibly less stable) in the ONNX Runtime session options. This removes intra-run non-determinism from thread scheduling races and keeps the *same-machine* determinism guarantee airtight for tests and CI, at some throughput cost (likely irrelevant at <10 new docs/night; relevant during the one-time 135k backfill, where it's still an offline batch job, not latency-sensitive).
- **Verdict:** transformer embeddings are "deterministic enough" for this product's actual constraint (no runtime network dependency + reproducible-on-this-machine batch/test behavior), but they are **not** the same category of "deterministic" as `DeterministicEmbedder`. Treat this distinction explicitly in requirements/tests: don't assert byte-identical vectors from a transformer model across CI runners of different architecture; do assert byte-identical vectors from repeated runs on the same runner.

## Local Model Acquisition vs. REQ-040

REQ-040 forbids a **runtime** dependency on an external model/service — it does not forbid a one-time local artifact download during setup, the same way the product already vendors/downloads other local dependencies. Two REQ-040-safe patterns:

1. **One-time download, then fully offline:** `@huggingface/transformers`'s default behavior downloads the ONNX model + tokenizer files from the Hugging Face Hub on first use and caches them locally (default cache dir, override via `env.cacheDir`). After that first fetch, all inference is 100% local/offline — no network call per-embed. This mirrors how the product already treats other one-time setup artifacts (e.g., guided init).
2. **Fully vendored, zero network ever:** Set `env.allowRemoteModels = false` and `env.localModelPath = "<repo-or-appdata>/models"`, and ship the ~23–35MB quantized ONNX + tokenizer JSON files as a bundled asset (checked into a release artifact or fetched once by an explicit `memory init --with-embeddings` step, not implicitly at runtime). This is the stricter interpretation and the one to prefer if "no runtime service" is read strictly to include "no implicit first-run download."

**Recommendation:** implement pattern 2 (explicit, one-time, opt-in vendoring step under an explicit CLI command), so the daemon and MCP server never have implicit network access, and the mandatory-adapter-gating language in PROJECT.md ("External models are optional adapters, never a local correctness dependency") is satisfied literally — the deterministic keyword-hash embedder remains the zero-dependency default; the transformer embedder is an explicit, separately-installed adapter.

## Why exact brute-force (sqlite-vec) beats true ANN here

The milestone's actual pain point (from PROJECT.md) is the **shared-term all-pairs trace algorithm being O(n²)** across summaries — not that O(n) brute-force cosine scanning is too slow. sqlite-vec's brute-force scan is O(n) per query, which already converts the trace step from O(n²) to O(n) per new/changed summary — that's the fix the milestone needs. At the stated scale (135,366 existing rows, <10/night incremental growth), a 384-dim brute-force cosine scan over ~135k rows is a single-digit-to-low-hundreds-of-milliseconds SQLite query (per public sqlite-vec benchmarks: sub-100ms for 384-dim @ 100k rows), which is fine for both a nightly incremental trace pass and interactive MCP recall. sqlite-vec's own documented limitation is scaling toward ~1M+ rows without an ANN index — this project is not there and is not projected to get there from normal usage (135k organic growth over the product's whole lifetime so far, at <10/night incoming).

True ANN (`hnswlib-node`, `usearch`) trades exactness for sub-linear scaling, but that trade only pays off well past this project's current/projected scale, and it introduces the one form of non-determinism this codebase has otherwise engineered out everywhere else: HNSW graph construction uses per-node random level assignment and is sensitive to insertion order, so an index rebuilt from the same 135k summaries in a different order (e.g., after a migration or a different-history backfill run) is not guaranteed to produce byte-identical neighbor rankings. Given this product's stated philosophy — deterministic local operation, external/complex components kept as strictly optional adapters — adding an approximate index before it's load-bearing is a determinism regression for no current performance benefit.

**Recommendation:** ship sqlite-vec now. Revisit true ANN only if/when summary count approaches ~500k–1M *and* brute-force query latency is empirically measured to be a problem (nightly batch trace step and/or interactive recall latency both have headroom today).

## Embedding Dimensionality Trade-offs

| Dim | Storage @ 135,366 rows (float32) | Storage @ 1M rows | Recall quality | Notes |
|---|---|---|---|---|
| 64 (current `DeterministicEmbedder` default) | ~35MB | ~256MB | Weak — bag-of-hashed-tokens, no real semantics, high collision rate at 64 buckets | Fine as the always-on fallback; not meant to carry recall quality |
| 384 (MiniLM/bge-small/gte-small) | ~208MB | ~1.5GB | Strong for short-document sentence-level retrieval — this is the standard, most-validated dimensionality for RAG-style semantic search at this corpus size | **Recommended** — best quality/cost ratio for this workload; every mainstream "small" sentence-transformer targets 384 |
| 768 (mpnet-base, larger BGE/GTE variants) | ~416MB | ~3GB | Modestly better MTEB scores than 384-dim small models, but the gap is small for short conversational-summary text (not long-document retrieval) | Not recommended for this corpus — 2× storage and 2–3× inference latency for a quality delta unlikely to be perceptible on personal conversational summaries; reconsider only if 384-dim recall proves inadequate in practice |

sqlite-vec supports storing vectors as `float32`, `int8`, or 1-bit binary-quantized columns in the same `vec0` virtual table, so if 384-dim float32 storage becomes a concern at very large scale, int8 quantization (~4× smaller, small recall cost) is a drop-in follow-up without changing the embedding model.

## Integration Points

1. **New `Embedder` implementation**, e.g. `TransformerEmbedder implements Embedder`, in `src/embeddings/` alongside the existing `DeterministicEmbedder`. Same interface (`provider`, `model`, `dimensions`, `embed(text): Promise<Embedding>`) — `MemoryRetriever` and `memory-service.ts` already accept any `Embedder` via constructor injection and already guard on `provider`/`model`/`dimensions` matching before trusting a stored embedding (`embeddingScore()` in `memory-retriever.ts`), so swapping embedders is additive, not a rewrite. Model loading (transformers.js `pipeline("feature-extraction", ...)`) should be initialized once and reused, not per-call.
2. **`Summary.embedding`** stays the source of truth in SQLite as today (JSON or BLOB column) for provenance/audit and for the keyword-hash fallback path; sqlite-vec's `vec0` virtual table becomes a **secondary, queryable index** over the same vectors (keyed by `summary.id`) purely for fast KNN — it does not replace the existing `Summary.embedding` field, it accelerates lookups against it. Keep them in sync inside the store write path (`saveSummary`), not as a separate out-of-band job, or add a rebuild-from-source command for recovery.
3. **`SqliteStore`** must construct its `DatabaseSync` with `{ allowExtension: true }` and call `sqliteVec.load(db)` once at startup, guarded so environments without the extension (or the `InMemoryStore` test double) still function via the existing brute-force `cosineSimilarity` path — i.e., sqlite-vec is an optional acceleration layer, not a hard dependency of `MemoryStore`, mirroring the existing "embedder is optional, falls back to keyword overlap" pattern already in `memory-retriever.ts`.
4. **Trace algorithm rewrite** (the actual milestone driver): replace the shared-term all-pairs scan with `SELECT summary_id FROM vec_summaries WHERE embedding MATCH ? AND distance < threshold ORDER BY distance LIMIT k` (or equivalent) per new/changed summary — O(n) per new item via sqlite-vec instead of O(n²) across the whole corpus, with the daemon's forward-only/incremental design already specified in PROJECT.md.
5. **Backfill of 135,366 existing summaries**: a one-time offline batch script, not the daemon's hot path. With `intraOpNumThreads` pinned and FP32, expect low-double-digit total minutes on the stated 18-core dev box; must be resumable/idempotent (mirrors the project's existing resumable-checkpoint pattern from the v1.0 bootstrap phase) in case of interruption over 135k rows.

## What NOT to Add

| Avoid | Why | Use Instead |
|---|---|---|
| `sqlite-vss` | Deprecated/unmaintained by its own author in favor of `sqlite-vec`; historically required a heavier Faiss-based native build with worse portability | `sqlite-vec` |
| `hnswlib-node` / `usearch` / any HNSW-family ANN index, *right now* | Introduces the one determinism regression this codebase has otherwise avoided everywhere else (insertion-order/RNG-sensitive graph construction, approximate top-k), for a performance problem the project does not yet have at 135k rows growing at <10/night | `sqlite-vec` exact brute-force scan; revisit ANN only past ~500k–1M rows with measured latency problems |
| `voy-search` | In-memory-only, WASM, no persistence story for a long-lived daemon over 135k+ rows | `sqlite-vec` |
| `node-llama-cpp` for embeddings specifically | Pulls in a second, heavier native-binding surface (llama.cpp) purely for embeddings when transformers.js/ONNX already covers this need with a lighter, more standard toolchain; only worth it if the project later also wants local LLM generation and can share the dependency | `@huggingface/transformers` |
| `onnxruntime-node` used directly without transformers.js | Forces hand-rolling WordPiece/BPE tokenization to exactly match the chosen model's training-time tokenizer — easy to get subtly wrong (off-by-one truncation, special-token handling), which silently degrades embedding quality without erroring | `@huggingface/transformers`, which bundles the correct tokenizer per model |
| Any embedding model requiring FP16/BF16 execution providers, GPU/CoreML/CUDA execution providers | Literature flags FP16/BF16 as visibly less numerically stable than FP32, and GPU execution paths are non-deterministic by nature (parallel kernel scheduling) — actively works against this project's determinism goals for negligible latency benefit at this corpus size | FP32, CPU execution provider only |
| Implicit first-run network download of the model at daemon/MCP-server startup | Risks violating the strict reading of "no runtime service" if the model isn't already cached — a background daemon silently reaching out to huggingface.co on first embed is the kind of behavior REQ-040's adapter-gating language is meant to prevent | Explicit, separately-invoked `memory init --with-embeddings` (or similar) one-time fetch/vendor step, decoupled from daemon startup |
| `@xenova/transformers` (legacy v2.x package name) for new code | Superseded by `@huggingface/transformers` (the actively maintained v3+/v4 line); `@xenova/transformers` is now the frozen legacy package | `@huggingface/transformers@4.2.0` |

## Open Questions

- **Exact model pin**: `Xenova/all-MiniLM-L6-v2` vs `Xenova/bge-small-en-v1.5` vs `Xenova/gte-small` — all are viable 384-dim options; final pick should be settled with a small offline recall-quality spot check against this project's actual summary text (conversational summaries, not general web text), not from benchmark leaderboards alone.
- **Quantized vs FP32 model weights**: quantized (int8/q8) ONNX weights are ~4× smaller and faster but introduce additional (small) numerical deviation from the reference FP32 model — needs an explicit decision on whether "deterministic" for this milestone means "reproducible on this machine" (quantized is fine) or "matches published reference embeddings" (use FP32).
- **Vendoring mechanism**: whether the one-time model fetch belongs in `memory init`, a dedicated `memory:embeddings:setup` script, or an npm postinstall step — needs a decision aligned with how the project already handles other one-time local setup (guided init from Phase 7).
- **int8/binary quantization inside sqlite-vec**: worth adopting immediately for storage, or defer until the 135k backfill is observed in production DB size — current float32 estimate (~208MB for 135k rows at 384-dim) is likely fine unmodified given the existing ~3.5GB DB baseline, so this is a low-urgency follow-up, not a blocker.
- **CI/test determinism strategy for the transformer embedder**: recommend asserting embedding-vector snapshot equality only within a single CI runner architecture (or skip byte-exact assertions for the transformer path entirely and instead assert on cosine-similarity-based behavior, e.g., "near-duplicate texts score above threshold X"), since cross-architecture bit-exactness is not guaranteed per the Determinism Analysis above.
